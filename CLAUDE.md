# aish

LLM-агент, встроенный в живой bash пользователя. Go, без внешних сервисов, кроме API модели.

Суть: `aish` запускает `bash -i` в PTY, перехватывает ввод до того, как bash его разберёт.
Строка с заглавной буквы, не являющаяся командой, уходит в LLM; всё остальное исполняет bash.
Агент не запускает подпроцессы для команд — он отдаёт их живому shell пользователя, и тот
исполняет их у себя (`eval` внутри `__aish_ask`), поэтому `cd`, `export`, функции и алиасы
сохраняются между вызовами.

Пользовательская документация — `README.md`. Незакрытые задачи и известные проблемы — `tasks/`,
по файлу на задачу; как задачи пишутся и исполняются — раздел «Задачи и параллельная работа».

## Сборка и проверки

```sh
go build -o aish ./cmd/aish   # бинарь ./aish в корне — артефакт, он в .gitignore
go test ./...
go vet ./...
```

Тесты есть у всех пакетов с логикой, включая `cmd/aish`; они чистые (без PTY и сети;
`mcp` запускает свой тестовый бинарь как stub-сервер, `llm` ходит в `httptest`, `rpc` слушает
временный unix-сокет, `tools` запускает скрипты на `/bin/sh`). После изменений в `internal/shellinit/init.bash` обязательно гоняй
`go test ./internal/shellinit` — он проверяет скрипт реальным bash.

Проверить руками: `./aish` открывает новую сессию, `./aish --resume` продолжает последнюю.
Внутри уже запущенного aish второй экземпляр не поднимется (`AISH_SOCK` непуст).

## Архитектура

```
терминал ⇄ proxy (PTY, фильтр маркеров, журнал сессии, unix-сокет $AISH_SOCK,
               ⇅ байты насквозь    агент: LLM, инструменты, политики, MCP)
           bash --rcfile $AISH_RUN/rc        rc = ~/.bashrc + init.bash
               Enter → bind -x __aish_route  → текст → __aish_ask '…'
                                                        ↓ JSON-RPC agent_start / agent_resume
                                   aish agent start/resume (тонкий клиент: передал, ждёт)
```

Два вида процессов:

- **прокси** (`aish` без аргументов) — долгоживущий, владеет сессией, PTY, сокетом и агентом
  (`agent.Agent` в `internal/proxy/agent.go`): цикл запроса крутится в нём;
- **команды** (`aish agent start|resume`, `aish tool`, `aish session`, `aish expand`, `aish compact`,
  `aish status`, `aish model`, `aish resume`, `aish mcp`, `aish skills`) — короткие
  процессы *внутри* shell, общаются с прокси по JSON-RPC через `$AISH_SOCK`. `aish resume` вне
  aish сам становится прокси с выбранной сессией.

Состояние живёт только в прокси. `aish agent start` передаёт текст запроса, cwd и окружение
shell (`rpc.AgentParams`) и держит соединение, пока прокси работает: ответ приходит, когда агент
оставил команду для shell или закончил. Ctrl+C приходит клиенту (он в foreground PTY), тот зовёт
`agent_cancel` и ждёт ответа на запрос — агент дописывает прерывание и убирает спиннер *до* того,
как bash напечатает промпт; второй Ctrl+C закрывает соединение, что отменяет запрос само по себе.

### Пакеты

| пакет | роль |
|---|---|
| `cmd/aish` | разбор argv, все подкоманды |
| `internal/proxy` | PTY, фильтр маркеров, запись вывода, сворачивание, Ctrl+O-вьюер, RPC-сервер; `agent.go` — агент в прокси: адаптеры `Journal`/`Shell`/`UI`, провайдер и политики между запросами, ввод `[y/N]` |
| `internal/shellinit` | `init.bash` (встроен через `go:embed`) — вся интеграция с bash |
| `internal/agent` | цикл запроса: LLM-ход → инструменты → bash-команда или финальный ответ; библиотека без RPC и stdout — журнал, shell и терминал приходят интерфейсами `Journal`, `Shell`, `UI` |
| `internal/session` | журнал сессии, JSONL в `~/.local/share/aish/sessions/`; рядом состояние, имя, lock; список и поиск для `aish resume` |
| `internal/bashstate` | состояние shell (переменные, функции, алиасы, опции, cwd) из дампа `__aish_dump`: разбор, дифф, скрипт восстановления |
| `internal/llm` | провайдер-нейтральный интерфейс + Anthropic и OpenAI |
| `internal/tools` | встроенные инструменты, внешние из `~/.config/aish/tools/`, CLI-разбор |
| `internal/mcp` | клиент MCP (stdio, Streamable HTTP), менеджер серверов в прокси, обёртки-команды, схема→CLI |
| `internal/skills` | скиллы Claude Code (`SKILL.md`): поиск от `~` и `/` до cwd, фронтматтер, скилл как `tools.Tool`, чей вызов отдаёт инструкцию с подставленными аргументами; `disable-model-invocation` — только команда, `loadTools` для агента их пропускает |
| `internal/policy` | Rego (OPA), парсинг bash-строки в список argv через `mvdan.cc/sh` |
| `internal/capture` | очистка вывода PTY от ANSI/`\r`, буфер «голова+хвост», усечение |
| `internal/markdown` | потоковый рендер markdown в терминал, подсветка через chroma |
| `internal/rpc` | один JSON-запрос на соединение, unix-сокет; `AgentParams`/`Status` — что команды носят в прокси и обратно |
| `internal/config` | `~/.config/aish/config.toml` поверх дефолтов |

### Поток одного запроса

1. Enter — макрос `\C-x\C-a\C-x\C-b`: `__aish_route` (`bind -x`) решает, bash это или LLM, затем
   `accept-line`. Запрос переписывается в `__aish_ask '<текст>'`; команда для bash остаётся как
   есть, а `__aish_mark` готовит для `PS0` маркер `cmd-start`.
2. `__aish_ask` затирает эхо readline (`__aish_unecho`), кладёт в историю набранное
   пользователем (`history -s`), печатает `ask-start` и запускает `aish agent start -- …`, который
   шлёт прокси `agent_start` с текстом, cwd и окружением shell и ждёт.
3. Прокси (`Proxy.request`) под `reqMu` готовит агента (`prepare`: свежий `config.Load`, модель и
   effort этого shell, провайдер — тот же объект, пока не сменились модель/effort/ключ, политики
   из `policy.Cache` по mtime, реестр инструментов для cwd: встроенные, внешние, скиллы,
   `mcp.Local`) и зовёт `Agent.Start`. `drive` крутит цикл: `turn` (запрос к модели) → `call` для
   каждого pending tool call, каждый вызов сначала проходит политику. Всё, что агент печатает, идёт
   через `UI` → `p.emit` под `p.mu`, с `\n` → `\r\n` (терминал в raw-режиме, PTY этого больше не делает).
4. Инструменты, кроме `bash`, исполняются в прокси с cwd и окружением shell (`tools.Exec`,
   `ExecuteIn`: относительный `path` встроенных — от cwd shell, внешние — `cmd.Dir`/`cmd.Env`).
   Внешние печатают вывод вживую в фолд (`UI.Live`), встроенные — одну строку, а многострочный
   результат отдают для Ctrl+O (`UI.Fold`).
5. `bash` — особый случай: агент печатает команду (`showBash`, колонка — через `UI.CommandAt`),
   пишет её в `$AISH_RUN/next.cmd`, id вызова — в `next.id` (`Shell.HandOff`), и `agent_start`
   возвращается; клиент выходит. Пока `next.cmd` не пуст, `__aish_ask` читает и
   опустошает его, печатает `agent-start;<id>;<команда>`, исполняет `eval "$cmd" </dev/null`,
   печатает `agent-end;<id>;<rc>;<cwd>` и запускает `aish agent resume <id> <rc>` → `agent_resume`.
   Прокси копит (и сворачивает) вывод между этими маркерами; `Agent.Resume` забирает его через
   `Shell.Wait` (`Proxy.wait`) и продолжает цикл с записями, оставшимися в памяти: журнал
   перечитывается только если сменился его ID или длина (`clear`, `aish resume` посреди запроса).
6. Агент закончил, не оставив команды, — `__aish_ask` возвращается, и `__aish_precmd` печатает
   `cmd-end`. По нему прокси снимает `asking`, а команды агента, прерванные Ctrl+C (без
   `agent-end`), записывает с кодом 130 — их подберёт `closePending` следующего запроса.

### Маркеры

OSC-последовательности `\e]6973;<nonce>;<kind>;<payload>\a`, вырезаемые прокси (`internal/proxy/markers.go`),
полный список с форматом payload — в шапке `internal/shellinit/init.bash`. Все пять — `cmd-start`,
`cmd-end`, `ask-start`, `agent-start`, `agent-end` — печатает `init.bash`; агент маркеров не печатает:
он в прокси и говорит ему напрямую (`UI.Live`/`Fold`/`CommandAt` в `internal/proxy/agent.go`).

`<nonce>` — случайная строка на каждый запуск прокси, лежит в `$AISH_RUN/nonce`; `init.bash` при
загрузке читает её в `__aish_nonce`. Последовательность с чужим nonce
(`cat` файла с маркерами, вывод прежней сессии) `Filter` отдаёт как обычный текст.

Если добавляешь маркер — правь обе стороны: место в `init.bash`, где он печатается (с nonce:
`$__aish_nonce`), и `Proxy.marker`, и допиши его в шапку `init.bash`. Payload не должен
содержать `\a` и `\e` — в том числе `$PWD`: `\a` обрывает маркер, а на `\e`
`Filter` считает его прерванным и выбрасывает. В bash это делается через `${var//[$'\a\e']/}`.

## Что легко сломать

- **`init.bash` исполняется в shell пользователя.** Любая переменная без префикса `__aish_`
  или утечка в окружение — баг. Не меняй `set -e/-u`. `HISTIGNORE`, `PS0` и `PROMPT_COMMAND`
  из `~/.bashrc` дополняются, а не заменяются; `PS1` не трогается вовсе.
- **`PROMPT_COMMAND` бывает массивом** — ветка в конце `init.bash` обрабатывает оба случая.
- **`__aish_precmd` должен вернуть исходный `$?`**, иначе сломается `$?` в пользовательском
  `PS1`.
- **В истории — то, что набрал пользователь.** Переписанную строку `__aish_ask '…'` отсекает
  `HISTIGNORE` (паттерн дописан навсегда), а `__aish_ask` кладёт вместо неё исходный текст через
  `history -s`. Команды агента идут через `eval`, мимо readline, и в историю не попадают.
- **Команда агента исполняется `eval` внутри функции `__aish_ask`**, stdin — `/dev/null`.
  Отсюда: `!` не раскрывается (history expansion бывает только у строк из readline);
  `local` и `declare` без `-g` живут до конца запроса и в состояние сессии не попадают;
  `return` выходит из `__aish_ask` и обрывает цикл без `agent resume`; `$1` — текст запроса.
- **Весь доступ к полям `Proxy` под `p.mu`.** `output`, `marker`, `key` и RPC-обработчики идут
  из разных горутин; запись в терминал тоже под локом, иначе Ctrl+O-вьюер перемешается с выводом.
  Агент пишет в терминал через `ui.Write` → `p.emit` под тем же локом, но сам цикл агента
  (`Proxy.request`) под `p.mu` не держится — он долгий, лок берётся на каждую запись.
- **Агент в прокси — один на shell и один запрос за раз** (`reqMu`). `Agent` хранит записи
  журнала между `Start`/`Resume`; при `Start` они перечитываются целиком, при `Resume` — только
  если журнал сменился (`Journal.ID`/`Len`). Паника в агенте ловится в `request` и уходит
  клиенту ошибкой — прокси, а с ним shell, падать не должен. cwd и окружение берутся из
  `rpc.AgentParams` клиента, не из процесса прокси: `os.Getwd`/`os.Getenv` в коде агента и
  инструментов — баг (ключ API — через `cfg.KeyFrom(ex.Getenv)`).
- **Вопрос `[y/N]` читает прокси** (`Proxy.askKey`, пока `p.ask != nil`): ввод не доходит до PTY,
  эхо печатает прокси; Ctrl+C пропускается в PTY, чтобы прервать клиента и с ним запрос.
- **RPC-вызов ограничен по времени.** `Client.Call` ждёт ответа `rpc.CallTimeout` (10 с);
  метод, который в прокси может работать дольше (`agent_start`/`agent_resume`/`compact`,
  `mcp_list` с `wait`, `mcp_call`), клиент зовёт через `CallContext` со своим контекстом
  (`cmd/aish/agent.go` — без дедлайна, с отменой по Ctrl+C). Обработчик обязан
  уважать `ctx`: `rpc.Serve` отменяет его, когда клиент закрыл соединение (убит, Ctrl+C,
  таймаут). Старт MCP-сервера от `ctx` не зависит — его ждут и другие.
- **Каждому tool call нужен result.** Прерывание по Ctrl+C оставляет «висящие» вызовы —
  `Agent.Start` закрывает их синтетическими результатами (`closePending`). Не ломай этот инвариант, Anthropic
  API отвергает сообщения без парных результатов.
- **`Entry.Raw`** хранит оригинальное сообщение ассистента от провайдера (thinking-блоки,
  подписи) и воспроизводится дословно, если совпали провайдер и модель. Не «нормализуй» его.
- **`clear`/Ctrl+L** обнуляют сессию (`Proxy.cleared`): модель видит только то, что на экране.
  Логика определения очистки — `internal/proxy/screen.go`, альт-экран (vim, less) не считается.
- **`KindSummary`** (от `aish compact`) заменяет всё, что было до неё: и `Messages`, и
  `Agent.load`, и подсчёт токенов работают с `session.Current(es)`. Новое место, которое читает
  журнал для модели, тоже должно начинать с `Current`.
- **Модель и effort переключаются на shell, а не в конфиге**: `aish model` пишет их в прокси
  (rpc `model`, параметры задают обе величины сразу, `""` — effort по умолчанию), агент получает
  `p.model`/`p.effort` поверх `cfg` (`Proxy.prepare`; `shellConfig` в `cmd/aish` — для `aish model`); оба сохраняются в
  `<id>.state` и восстанавливаются при resume. Сырые сообщения (`Entry.Raw`) воспроизводятся
  только при совпадении и провайдера, и модели. `max_tokens = 0` значит «по effort»
  (`Config.ReplyTokens`), поэтому провайдеры читают его только через этот метод.
- **Статус справа от промпта рисует прокси** на маркере `cmd-end` (`proxy/status.go`) через
  `\e7 … \e8`, `PS1` не трогается. Всё, что печатается между `cmd-end` и промптом, может его сдвинуть.
- **Состояние shell снимается до `cmd-end`.** `__aish_precmd` один раз пишет базу
  (`$AISH_RUN/state.base`, shell сразу после `~/.bashrc`), исполняет и опустошает
  `$AISH_RUN/restore.bash`, если он не пуст, и пишет `$AISH_RUN/state` — всё это *до* печати
  `cmd-end`, потому что прокси читает дамп по этому маркеру (`Proxy.saveState`). В сессию
  (`<id>.state`) идёт только дифф `Diff(base, cur)`. Дамп — без fork, на каждом приглашении:
  не добавляй туда внешних команд. Что пропускается (`_*`, `AISH_*`, `BASH_*`, `READLINE_*`,
  readonly, переменные bash) — `internal/bashstate`; новое служебное имя без этих префиксов попадёт в сессию.
- **Переключение сессии внутри shell** (`rpc resume`) пишет в `restore.bash`
  `Diff(cur, Apply(base, target))` — то есть заодно откатывает изменения прежней сессии — плюс
  `export AISH_SESSION=<id>`, и ставит `Proxy.switched`, чтобы команда `aish resume` не попала ни в один журнал. Агенту
  (`p.asking`) переключаться нельзя.
- **Сессию держит один aish**: `<id>.lock` (flock) берёт `Run`/`resume`, `Clear` переносит его на
  новый ID. `Latest` и пикер пропускают открытые сессии.
- **Nonce маркеров не передаётся через окружение** — только файлом `$AISH_RUN/nonce` (0600) и
  неэкспортируемой `__aish_nonce`. Из окружения его унаследует каждая команда, и он окажется в
  выводе того же `env`. Nonce защищает от данных, не от локального процесса: у того и так есть PTY.

## Конвенции

- Комментарии и идентификаторы — по-английски; документация в `*.md` — по-русски.
- У каждого пакета godoc-комментарий, объясняющий роль пакета в системе, а не перечень функций.
- Комментарий пишется, когда неочевидно **почему**; описывать *что* делает код не нужно.
- Ошибки — `fmt.Errorf` с контекстом, без своих типов ошибок.
- Никаких новых зависимостей без необходимости; текущий набор — см. `go.mod`.
- Форматирование: табы (gofmt), в `init.bash` тоже табы.

## Задачи и параллельная работа

Задачи лежат в `tasks/` (каталог в `.gitignore`), по файлу на задачу: `NN-<ID>-<Slug>.md`, где
`NN` — порядковый номер, `ID` — пункт плана (`2.N` — баги и небольшие улучшения, `1X` — этапы
рефакторинга). Пишет их скилл `create-parallel-task` (`.claude/skills/`), он же проверяет, что
новая задача не пересекается по файлам с открытыми.

Над разными задачами одновременно работают несколько агентов, каждый в своём worktree
(`.claude/worktrees/<name>`, ветка `worktree-<name>`), и все пушат в один `origin/master`.
Поэтому задача — ещё и договор о границах. В шапке: `**Файлы:**` — что она меняет (две открытые
задачи не называют одно и то же место), `**Зависит от:**` — чей результат ей нужен в
`origin/master`, `**Параллельно:** нет` — её запускают одну. Закрытой задача считается, когда её
имя (без `.md`) стоит в трейлере `Task:` коммита в `origin/master`.

### Flow агента в worktree

Файл задачи лежит вне worktree (`tasks/` не в git) — читай его по данному пути. В основном
checkout, где он лежит, ничего не меняй и git там не трогай.

1. **Начни с `origin/master`.** Worktree создаётся от локального `master`, который часто
   отстаёт: `git fetch origin && git rebase origin/master`. Прочитай задачу целиком и сверь ссылки
   `файл:строка` с кодом — он мог сдвинуться.
2. **Держись границ.** Меняй то, что перечислено в `**Файлы:**`. Если без правки чужого файла не
   обойтись — делай её минимальной и назови в отчёте. Не переименовывай, не переставляй функции,
   не чини попутно соседний код, не форматируй файлы целиком, не запускай `go mod tidy` — каждая
   такая правка оборачивается конфликтом у другого агента. Новую функциональность клади в новый
   файл: новый файл не конфликтует, конфликтует только строка регистрации. Новых файлов в
   `tasks/` не создавай — находки идут в отчёт.
3. **Общие файлы — точечно.** `cmd/aish/main.go` (switch подкоманд), `internal/proxy/proxy.go`
   (`marker`, `handle`), `internal/rpc/rpc.go` (методы), `internal/config/config.go`,
   `internal/tools/builtin.go`, шапка `init.bash`, `README.md` и `CLAUDE.md` правят все задачи
   сразу. Вставляй в логичное место списка (рядом с родственным, по алфавиту), а не в конец —
   в конец вставляют все, и там конфликт гарантирован. Документацию правь в том месте, которое
   назвала задача, соседние абзацы не переписывай.
4. **Проверь:** `gofmt -l .` пуст, `go build ./... && go vet ./... && go test ./...`; после правок
   `init.bash` — `go test ./internal/shellinit`. Критерий готовности из задачи проверен, а не
   «должен работать».
5. **Коммит** — один на задачу (несколько, только если задача сама так делит). Сообщение в стиле
   `git log`: тема по-английски в повелительном наклонении, тело — почему, последней строкой
   трейлер `Task: NN-ID-Slug` (имя файла задачи без `.md`). `./aish`, `tasks/`,
   `.claude/worktrees/` в `.gitignore`; стейджи файлы по именам.
6. **Пуш в master, не в ветку:**
   ```sh
   git fetch origin && git rebase origin/master
   go build ./... && go vet ./... && go test ./...   # ещё раз: сверху теперь чужие коммиты
   git push origin HEAD:master
   ```
   Отказ push (non-fast-forward) значит, что кто-то успел раньше — повтори с `fetch`. Конфликт при
   rebase решай, сохраняя обе стороны: чужой код не удаляют; после `git add` —
   `GIT_EDITOR=true git rebase --continue`. Если столкнулись две правки одной логики и неясно,
   что верно, — не пушь, опиши конфликт в отчёте. Никакого `--force`, `reset --hard`; ветку
   `worktree-*` в `origin` не пушь.
7. **Отчёт:** хэш коммита в `origin/master`, что сделано, где и почему отступил от задачи, что
   осталось и что заметил по дороге (кандидаты в новые задачи).

## Конфигурация и пути

- `~/.config/aish/config.toml` (путь переопределяется `$AISH_CONFIG`) — см. `config.Default()`.
- `~/.config/aish/tools/` — внешние инструменты (заголовок `# aish:desc` / `# aish:arg`,
  пример — `examples/tools/weather`).
- `~/.config/aish/policy/*.rego` — политики, запрос `data.aish.decision`,
  пример — `examples/policy/default.rego`.
- `~/.claude/skills/`, `~/.config/aish/skills/`, `.claude/skills/` от `/` до cwd — скиллы; обёртки
  в `$AISH_RUN/bin` получают только личные, проектные — через `aish tool NAME`.
- `~/.config/aish/mcp.yaml` (или `mcp_config`) — MCP-серверы; кэш списков инструментов —
  `~/.cache/aish/mcp/<server>.json`.
- `~/.local/share/aish/sessions/` — `<id>.jsonl` журналы, `<id>.state` состояние shell и модель
  (значения переменных открытым текстом, 0600), `<id>.name` имя, `<id>.lock`.
- `$AISH_RUN` — временный каталог сессии: `rc`, `sock`, `bin/` (обёртки инструментов),
  `nonce`, `next.cmd`, `next.id`, `state.base`, `state`, `restore.bash`. Удаляется при выходе.
- Переменные для shell (ставит прокси): `AISH_SOCK`, `AISH_RUN`, `AISH_BIN`, `AISH_TOOLS_PATH`
  (`init.bash` и скрипт восстановления добавляют его в начало `PATH`) и `AISH_SESSION` — ID
  сессии для пользователя и его скриптов. Сам aish `AISH_SESSION` не читает; переключение сессии
  его обновляет, а `clear`, который тоже меняет ID, — нет.
