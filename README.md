# aish — LLM внутри твоего bash

aish запускает твой обычный bash — с `~/.bashrc`, алиасами, промптом и историей — и подсаживает
в него ассистента. Набираешь команду — её исполняет bash. Пишешь фразу с заглавной буквы — отвечает
модель, которая видит всё, что происходило в терминале: команды, их вывод и прошлый разговор.

```
$ make
main.go:12: undefined: foo
? Почему не собирается?
⚙ read_file main.go
❯ grep -rn "func foo" .  (1 line · ctrl+o to expand)
В main.go вызывается foo(), но функция нигде не объявлена…
```

Ассистент работает в том же shell, что и ты: его `cd`, `export` и объявленные функции остаются
после того, как он закончил. Никаких подпроцессов и песочниц — он отдаёт команды твоему живому bash.

## Установка

```sh
go build -o ~/.local/bin/aish ./cmd/aish
export AISH_API_KEY=...        # или ANTHROPIC_API_KEY / OPENAI_API_KEY
aish                           # новая сессия
aish --resume                  # продолжить последнюю
aish resume                    # выбрать сессию из списка
```

Чтобы aish открывался в каждом новом терминале, сделай его командой терминала или допиши в конец
`~/.bashrc`:

```sh
[[ -z $AISH_SOCK && $- == *i* ]] && exec aish
```

## Команда или вопрос?

Строку, первое слово которой — команда, алиас или функция, выполняет bash, как бы она ни выглядела:
`git status`, `Rscript x.R`. Остальное уходит модели, если похоже на вопрос:

- начинается с заглавной буквы: `Как найти большие файлы?`, `Find big files` (`find` — команда,
  `Find` — нет);
- кончается на `?`: `ls?` (такой команды нет; а `ls foo?` выполнит bash — `ls` команда, `foo?` —
  шаблон имён файлов);
- это слова, а не shell: два слова и больше и ни одного из `` |&;<>()$`\= `` — `why does this fail`,
  `почему не собирается`.

Одно слово (`gti`) и строка с синтаксисом shell (`gti status | head`) достаются bash с его обычным
`command not found`. Цена третьего правила — опечатка из двух слов: `gti status` уйдёт модели, но
та видит контекст shell и ответит «ты имел в виду `git status`?». Для заглавных букв кириллицы
нужна UTF-8-локаль.

Правила настраиваются таблицей `[route]` в `config.toml`, здесь — значения по умолчанию:

```toml
[route]
capital = true    # строка с заглавной буквы
not_found = true  # слова, а не shell: то, на что bash ответил бы command not found
suffix = "?"      # строка, которая кончается на suffix; "" — правило выключено
min_words = 2     # сколько слов нужно для not_found
expand = true     # раскрывать $VAR и $(…) в запросе
```

С `not_found = false` такие строки достаются bash, а после первого `command not found` за сессию
aish подскажет префикс `?`. Свой `command_not_found_handle` (pkgfile, command-not-found) работает
как прежде для всего, что досталось bash. `[route]` читается при старте aish: после правки
перезапусти его.

Когда правила мешают, есть префиксы:

- `?текст` — точно модели: `?почему не собирается`; текст уходит как есть, без раскрытия `$VAR` и
  `$(…)`;
- `@файл …` — тоже модели, файл прикладывается к запросу (см. ниже);
- `/скилл …` — тоже модели, с инструкцией скилла; имя скилла первым словом (`fix-issue 123`)
  работает так же (см. «Скиллы»);
- `!команда` — точно bash; `!!`, `!$`, `!-2` и прочие history expansion работают как раньше.

Переменные и подстановку команд в запросе раскрывает сам shell: `Посмотри логи в $LOGDIR` и
`На какой ветке $(git branch --show-current)?` доходят до модели со значениями, и на экране видно
то, что ей ушло, а в истории остаётся набранное — повтор строки раскроется заново. Кавычки и
обратные кавычки остаются текстом (``Что делает `ls`?``); строку, которую shell не разобрал (`${`
без пары), модель получит как набрана. `$?` раскроется в код последней команды
(`Почему упало с кодом $?`), `$1` — в пустую строку; в вопросе про них самих `\$` защищает один
доллар, `?` в начале — всю строку; `expand = false` выключает раскрытие совсем. `$(…)` в запросе
выполняется, как выполнился бы в shell, — и во вставленном из буфера тексте тоже: смотри, что
вставляешь. Пока подстановка работает, на месте строки стоит тусклое `expanding…`; Ctrl+C прерывает
её, и запрос не уходит, но остаётся на экране и в истории, а `$?` — 130. Команды, читающие
терминал (`read`, запрос пароля), в подстановке не работают: терминал в это время в режиме
readline — эха нет, Enter приходит как `\r`.

В историю попадает то, что ты набрал, вместе с префиксом. На экране строка с вопросом отличается от
команд: `$` (или `#`) в конце промпта заменяется на `?`.

Ctrl+V (или Ctrl+Q) перед вставкой из буфера команду не портит: текст вставляется целиком, а не как
`^[[200~текст~`; перед Tab или Esc Ctrl+V, как и раньше, вставляет сам символ. Свою привязку `\C-v`
(в `~/.inputrc` или `~/.bashrc`) aish не трогает.

## Что умеет ассистент

Модель работает сама, без подтверждения каждого шага; ограничить её можно политиками (ниже).
Инструменты:

| инструмент | что делает |
|---|---|
| `bash` | команда в **твоём живом shell**: `cd`, `export`, функции сохраняются; вывод свёрнут |
| `read_file PATH [OFFSET] [LIMIT]` | читает файл с номерами строк |
| `write_file PATH [CONTENT\|-]` | пишет файл (содержимое аргументом или со stdin) |
| `edit_file PATH OLD NEW [REPLACE_ALL]` | точечная замена в файле |
| `ask_user` | спрашивает тебя, когда задача неоднозначна: до четырёх вопросов с вариантами, по одному на экране. `↑↓` или цифра — выбор, пробел — отметка, если можно несколько, «Other» — свой ответ, Enter — дальше, `←`/Backspace — назад, Esc — отмена. Остаётся сводка `заголовок: ответ`. Только для модели, командой не набирается |
| `tool_search` | загружает схемы отложенных MCP-инструментов — по именам (`select:A,B`) или по словам из имени и описания (см. «MCP-серверы»). Только для модели, командой не набирается |
| свои | исполняемые файлы из `~/.config/aish/tools/` |
| скиллы | `SKILL.md` из `~/.claude/skills/` и `.claude/skills/` |
| MCP | инструменты серверов из `~/.config/aish/mcp.yaml` |

`write_file` и `edit_file` пишут файл целиком или никак: во временный файл рядом, затем `rename`
поверх; симлинк остаётся симлинком, а с файла пропадают его ACL, xattr и биты setuid/setgid. Файл с
жёсткими ссылками, файл чужого владельца или группы и файл в каталоге, закрытом для записи, пишутся
на месте — без этой гарантии, но со всем, что у них было. FIFO и устройство `write_file` тоже пишет
на месте, а `read_file` и `edit_file` их не открывают.

Встроенные инструменты, внешние и MCP можно вызвать и самому: `aish tool read_file main.go 1 20`;
`aish tool` покажет полный список.

`Ctrl+C` прерывает и ответ, и команду, которую запустил ассистент; модель узнает, что её прервали.

### Файлы в запросе

Чтобы модель сразу получила файл, упомяни его через `@`: `Изучи заметки @*.md и скажи, что делать`.
Под запросом появится строка на каждый найденный файл — `@todo.md (12 lines)` — и модели не придётся
тратить ход на `read_file`.

- `@путь` — файл или папка (для папки — список файлов); `~` раскрывается, относительные пути — от
  текущего каталога;
- `@шаблон` — glob с `*`, `?`, `[…]` и `**` (`@src/**/*.go`); скрытые файлы, `.git` и `node_modules`
  берутся, только если названы явно;
- путь с пробелами — в кавычках: `@"мои заметки.md"`; знак препинания после упоминания к пути не
  относится, `user@host` упоминанием не считается;
- бинарные файлы пропускаются; лимиты — 40 KB на файл, 200 KB и 50 файлов на запрос, остальное
  модель дочитает сама;
- ненайденный файл отмечается под запросом: `@x.md: no such file`.

## Экран

**Ответы** рендерятся как markdown по ходу генерации: заголовки, списки, цитаты, ссылки как
`текст (url)`, таблицы в рамке (появляются целиком, когда дописаны), подсветка кода по языку
(стиль — `code_style`). Пока модель думает, крутится спиннер `⠋ thinking…`.

**Вывод команд ассистента** свёрнут: на экране только команда и статус у правого края её последней
строки — `(30 lines · exit 1 · ctrl+o to expand)`; счётчик строк обновляется, пока команда работает.
Так же выглядят вызовы других инструментов: `⚙ read_file …` — одна строка, обрезанная по ширине
терминала с `…`, статус у её правого края; однострочный результат (`wrote 4326 bytes to …`) идёт
строкой ниже. Если подсказка про Ctrl+O не влезает, статус короче — `(30 lines · exit 1)`, а в узком
терминале он уходит строкой ниже.
Команда длиннее трёх строк показывается первыми тремя и строкой `… (+N lines)`; целиком она видна
в Ctrl+O.
`fold_lines = N` показывает первые N строк, `-1` отключает сворачивание.

**Ctrl+O** открывает полноэкранный просмотр всего, что было свёрнуто за текущий или последний
запрос: вывод команд, результаты `read_file`, даже ещё работающую команду. Листать — `↑↓`/`j k`,
`PgUp PgDn`/пробел `b`, `g G`; закрыть — Ctrl+O, `q` или Esc. Работает в любой момент, в том числе
пока модель пишет. Если сворачивать было нечего, Ctrl+O достаётся readline или запущенной программе.
`aish expand` печатает свёрнутое прямо в терминал.

**Статус справа от промпта** — занятый контекст и модель: `34k/1.0M 3% · claude-opus-5`.
Он виден, пока строка ввода пуста: набранный текст его прячет, а стёртая до пустой строка возвращает.
Жёлтый от
70%, красный от 90%: пора сделать `aish compact` или `clear`. Строку рисует aish, а не `PS1`, так что
она уживается с любым промптом (starship и т. п.); в узком терминале не показывается, выключается
через `prompt_status = false`.
Ширину символов aish, как и `go-runewidth`, берёт из локали; если статус или рамки таблиц съезжают,
запусти aish с `RUNEWIDTH_EASTASIAN=0` (символы вроде `…` и `─` в одну колонку) или `=1` (в две).

**`clear`, `reset` и Ctrl+L** сбрасывают контекст: модель видит только то, что осталось на экране.
Сессия при этом та же — ID, имя и журнал не меняются, `aish session show` покажет и то, что было до
очистки. Очистка внутри vim, less и других полноэкранных программ не считается.

## Контекст и модель

- `aish status` — сколько контекста занято и как это посчитано (точное число токенов из последнего
  ответа модели плюс оценка всего, что появилось после), сколько команд и запросов с последнего
  compact, сколько токенов потрачено за сессию и сколько входных прочитано из кэша провайдера,
  профиль, провайдер, модель, её окно и effort, настройки и пути.
- `aish compact [о чём помнить]` просит модель кратко изложить сессию: запросы, что сделано, пути,
  ошибки, текущее состояние. Дальше модель получает только эту сводку и то, что было после неё.
  Журнал не стирается — `aish session show` покажет всё.
- Когда контекст переваливает за `compact_at` окна (по умолчанию 0.8), aish сам делает то же, что
  `aish compact`, перед следующим ходом модели — `compacted: 28k → 3.1k tokens` — и запрос идёт
  дальше со сводки: инструкции (CLAUDE.md) перечитываются, а запрос, на который модель ещё не
  ответила, уходит после сводки как набран. Если порог перейдён, пока ты работаешь в shell, статус
  справа от промпта помечает это `compact?`, а сводку делает следующий запрос — ход модели ради неё
  не тратится. Вторую сводку сразу за первой aish не делает: если порог всё ещё превышен из-за
  огромного результата последней команды, модель получает его урезанным (в журнале он целиком).
  Нужен известный размер окна — от API или `context_window`; `compact_at = 0` выключает.
  Ответ, который модель оборвала, упёршись в окно (`[aish: reply cut: the context window is full]`),
  тоже запускает сводку перед следующим ходом — даже при оценке ниже порога и неизвестном окне.
  Так же действует отказ API «prompt is too long» (у OpenAI — `context_length_exceeded`): aish
  делает сводку и повторяет ход, а если не помогло — запрос кончается ошибкой.
  Порог и число токенов, на котором он сработает, показывает `aish status` в строке `compact_at`.
- `aish model` — список моделей, которые отдаёт API, с размером окна; текущая отмечена `*`.
  `aish model ИМЯ` переключает модель **для этого shell**; насовсем — `model` в `config.toml`.
  Переключает только пользователь: `aish model` из команды ассистента получает отказ, как и
  `aish resume` и `aish clear`.
- Effort — насколько долго модель думает. `aish model high` меняет только его, `aish model
  claude-sonnet-5 xhigh` — модель вместе с effort, `aish model default` возвращает уровень, который
  модель выбирает сама. Уровни Anthropic: `low`, `medium`, `high`, `xhigh`, `max`; у OpenAI ещё
  `none` и `minimal`. Насовсем — `effort` в `config.toml` или `$AISH_EFFORT`. Если API не сообщает,
  какие уровни знает модель (так у cliproxyapi), неподходящий отвергнется на первом запросе. На
  `xhigh` и `max` лимит ответа поднимается с 32000 до 64000 токенов, если `max_tokens` не задан.
- Профиль (`[profiles.ИМЯ]` в `config.toml`, см. «Настройки») — другой endpoint целиком: провайдер,
  `base_url`, ключ, модель, effort. `aish model local` переключает shell на профиль `local` с его
  моделью и effort, `aish model local qwen3:8b` и `aish model local qwen3:8b high` — на другую
  модель и effort этого профиля. Первое слово сначала ищется среди профилей, потом среди моделей и
  уровней effort: модель с именем профиля дают вторым словом, после профиля. `aish model` без
  аргументов показывает и профили (текущий отмечен `*`), и модели текущего. Верхний уровень
  `config.toml` в этом списке — `root`: `aish model root` возвращает shell на него, поэтому профиль
  с именем `root` завести нельзя. Профиль, как модель и
  effort, — на этот shell, хранится в `<id>.state` и возвращается с `aish resume`. Статус справа от
  промпта называет профиль, если он не тот, что выбирает `config.toml`. Насовсем — `profile` в
  `config.toml` или `$AISH_PROFILE`. `root` — имя верхнего уровня и в `profile`/`$AISH_PROFILE`;
  профиль с другим `provider` без `effort` берёт уровень по умолчанию, а не верхнего уровня.

Подкоманды набираются только с `aish`, инструменты — только как `aish tool ИМЯ`: имён в shell aish
не занимает. Кому нужны короткие имена — алиасы в `~/.bashrc` под проверкой, что shell запущен в aish
(`$AISH_SOCK` задан уже до `~/.bashrc`):

```sh
if [[ -n ${AISH_SOCK-} ]]; then
	alias status='aish status' model='aish model' compact='aish compact'
	alias read_file='aish tool read_file'
fi
```

Алиас `clear` или `expand` перекроет системную команду, а алиас с именем скилла — скилл: тот останется
доступен как `/имя`.

## Сессии

Сессия — это журнал (команды, вывод, запросы, ответы) **плюс состояние shell**. По умолчанию сессия
живёт только в памяти aish и с выходом пропадает; на диск её кладут `aish clear save` и `aish new`,
и дальше она пишется насквозь. Сессии глобальные: любую можно продолжить из любого терминала, но
одну сессию держит только один aish.

- `aish --resume` продолжает самую свежую сессию, которую никто не держит.
- `aish resume` открывает список: имя или ID, когда использовалась, каталог, модель с профилем,
  если он не тот, что выбирает `config.toml` (`root` — его верхний уровень), число запросов,
  последний запрос. `↑↓`/`j k`,
  `PgUp PgDn`, `g G` — двигаться, Enter — продолжить, `r` — переименовать, `d` и `y` — удалить,
  `q`/Esc — выйти. `[this shell]` — сессия этого shell, `[open]` — занята другим aish.
- `aish resume ID|ИМЯ` — сразу, без списка; хватит однозначного начала ID или имени.
- Вне aish `aish resume` запускает aish с этой сессией. Внутри — переключает текущий shell: со
  следующего приглашения журнал и состояние уже той сессии, а изменения прежней откатываются.
  Переключаться может только пользователь, не ассистент. Несохранённая сессия, из которой
  переключились, теряется — `aish resume` об этом предупреждает.
- `aish clear` начинает новую несохранённую сессию; прежняя, если не сохранена, пропадает.
- `aish clear save [ИМЯ]` сохраняет текущую — журнал, состояние shell, имя — и начинает новую.
- `aish new [ИМЯ]` начинает новую сессию, которая сохраняется с первой записи; несохранённая
  прежняя пропадает. Имя — всё после команды, без кавычек: `aish new разбор логов`.
- `aish session rm ID|ИМЯ…` удаляет сохранённые сессии с диска — как и `aish resume`, по ID, имени
  или их однозначному началу. Сессию этого shell удалить нельзя (сначала `aish clear`), открытую в
  другом aish — тоже.
- `aish session prune --older 30d` удаляет сессии, которыми не пользовались 30 дней (`12h` — 12
  часов, `0d` — все); открытые остаются. Без `--older` берётся `sessions_ttl` из настроек: если он
  задан (`sessions_ttl = "30d"`), aish и сам удаляет такие сессии при каждом запуске. По умолчанию
  `"0"` — сессии хранятся, пока их не удалят.

Восстанавливается всё, чем shell отличается от свежезапущенного (после `~/.bashrc`): переменные
(в том числе неэкспортированные и массивы), функции, алиасы, `set -o`/`shopt`, текущий каталог,
профиль, модель и effort из `aish model`. Остальное окружение — `DISPLAY`, `SSH_AUTH_SOCK` и т. п. —
берётся из нового терминала, а не застревает из прошлого. Не восстанавливаются история команд
(у неё свой `HISTFILE`), `trap`, фоновые задачи, стек `pushd`, `readonly`-переменные, имена с `_`
в начале и переменные самого bash. Состояние снимается на каждом приглашении встроенными командами
bash, без fork.

Файлы сохранённых сессий лежат в `~/.local/share/aish/sessions/`: `<id>.jsonl` — журнал,
`<id>.state` — состояние shell (значения переменных открытым текстом; права 0600), `<id>.name` —
имя, `<id>.lock` — пока сессия открыта. `aish session show` печатает журнал.

Что не пишется на диск, задают два списка шаблонов в настройках (синтаксис — как у `HISTIGNORE`):

- `journal_ignore` — команды, чей вывод не попадает в журнал, а значит и к модели: по умолчанию
  `env`, `printenv`, `history`, `cat *credentials*` и всё с `secret`. Шаблон сверяется с каждой
  простой командой строки целиком, так что `sudo env` и `env | grep X` тоже подходят; в журнале
  остаётся сама команда с выводом `[not recorded]`.
- `state_ignore` — переменные, которые не попадают в `<id>.state` и не восстанавливаются: по
  умолчанию `*TOKEN*`, `*SECRET*`, `*KEY*`, `*PASSWORD*`, `AWS_*`.

Пустой список (`journal_ignore = []`) отключает фильтр. Это защита от случайного попадания в
журнал, не маскирование: `cat secret.txt | base64` отфильтруется, а `grep -r token .` — нет.

Секреты в том, что уходит модели, маскируются: вывод команд, файлы из `@`, инструкции, скиллы,
контекст хуков `user-prompt` и результаты инструментов проходят через набор регулярок (ключи AWS,
GitHub, OpenAI, Slack, блоки `PRIVATE KEY`, `password=`/`token:`/`api_key=` и т. п.), от значения
остаются первые четыре символа — `AKIA***`. Сам запрос пользователя не трогается, журнал и экран
тоже: `aish session show` показывает то, что видел пользователь. Свои регулярки — `mask` в
`config.toml` (группа в скобках прячет только её, остальное — ориентир для модели), встроенные
выключает `mask_defaults = false`; `aish status` показывает, сколько их.

## Инструкции (CLAUDE.md)

Как в Claude Code, модель получает инструкции из файлов: глобальные `~/.claude/CLAUDE.md` и
`~/.config/aish/CLAUDE.md`, и по папкам — `CLAUDE.md`, `.claude/CLAUDE.md`, `AGENTS.md`,
`CLAUDE.local.md` в каждой папке от `/` до текущей. Файл читается при первом запросе из папки
(под запросом появляется его путь), попадает в сессию один раз и перечитывается, если изменился.
После `clear` и `aish compact` инструкции загружаются заново.

## Свои инструменты

Инструмент — любой исполняемый файл в `~/.config/aish/tools/` с шапкой
(пример — `examples/tools/weather`):

```sh
#!/bin/sh
# aish:desc Show the weather forecast for a city
# aish:arg city string City name
# aish:arg days? integer Optional argument
# aish:arg body stdin Passed on standard input
```

Вызывается он так же, как набирают `aish tool NAME`: обязательные аргументы — позиционно, в порядке
шапки; необязательные (`name?`) — флагами `--name значение` (булев — просто `--name`);
`stdin`-аргумент приходит на стандартный ввод; объекты и массивы — JSON. Каждый переданный аргумент
есть и в `$AISH_ARG_<NAME>`, так что необязательные проще читать оттуда: `${AISH_ARG_DAYS:-1}`.
`aish tool NAME -h` показывает форму вызова, для этой шапки — `weather CITY [--days DAYS] BODY|-`.

## Скиллы

Скиллы Claude Code работают без изменений: каталог с `SKILL.md` (YAML-фронтматтер с `description`,
дальше инструкция) и файлами, на которые она ссылается. Имя — `name` из фронтматтера или имя каталога.
Ищутся в `~/.claude/skills/`, `~/.config/aish/skills/` и `.claude/skills/` каждой папки от `/` до
текущей; одноимённый скилл ближе к текущей папке перекрывает дальний (в Claude Code наоборот).

```
$ aish skills
fix-issue [issue-number]  ~/.claude  [not for the model] Fix a GitHub issue
pdf-processing            ~/.claude  Extract text and tables from PDF files…
release-notes             ./.claude  Draft release notes from the git log…
$ fix-issue 123                      # модель получает инструкцию с подставленным 123 и выполняет её
$ Сделай релиз /release-notes v2.1   # то же, упоминанием в любом месте запроса
$ aish tool release-notes v2.1       # просто напечатать инструкцию
```

- Скилл — обычный инструмент: модель видит имя и описание и вызывает его сама, когда задача
  подходит. Инструкция попадает в контекст только при вызове — вместе с путём к каталогу и списком
  его файлов, чтобы модель открыла `reference.md` или запустила `scripts/*`. `${CLAUDE_SKILL_DIR}`
  заменяется на путь каталога.
- Аргументы — как в Claude Code: в shell это слова после имени команды (`fix-issue 123 "with
  tests"`). `$ARGUMENTS` — вся строка, `$N` и `$ARGUMENTS[N]` — N-е слово с нуля, `$name` — слово с
  позицией `name` в списке `arguments` фронтматтера; `\$1` — буквальный `$1`. Если ни одна
  подстановка аргументы не взяла, они дописываются в конец строкой `ARGUMENTS: …`. `argument-hint`
  показывается в `aish skills` и в описании для модели. При упоминании внутри фразы (`Сделай релиз
  /release-notes v2.1`) `$ARGUMENTS` — вся фраза без `/имя`: `Сделай релиз v2.1`.
- `disable-model-invocation: true` прячет скилл от модели — остаётся вызов пользователем: `deploy
  prod` или `/deploy prod` отдаёт инструкцию модели, сама она его не позовёт. Удобно для действий
  вроде деплоя.
- Скилл набирается как команда (`fix-issue 123`) или упоминается как `/имя` в любом месте запроса.
  Инструкция с подставленными аргументами прикладывается к запросу, как файл по `@`, — под запросом
  строка `/fix-issue (~/.claude/skills/fix-issue/SKILL.md)`; аргументы — слова запроса без самого
  упоминания. Имя, занятое командой, функцией или алиасом, исполняет bash, а скилл остаётся
  доступен как `/имя`. Проектные скиллы видны сразу, перезапуск не нужен.
- `allowed-tools` передаётся модели как подсказка; остальные поля фронтматтера не используются.
- `aish skills` показывает скиллы и проблемы с ними: битый фронтматтер, нет `description`, имя с
  недопустимыми символами (можно буквы, цифры, `-` и `_`), `name` не совпадает с каталогом, имя
  занято инструментом или командой в `PATH`.

## Сабагенты

aish читает описания сабагентов Claude Code: файлы `NAME.md` в `~/.claude/agents/`,
`~/.config/aish/agents/` и `.claude/agents/` каждой папки от `/` до текущей (только прямо в каталоге,
без подкаталогов). Как и у скиллов, одноимённое описание ближе к текущей папке перекрывает дальнее.

```markdown
---
name: reviewer
description: Reviews the diff before a commit and points out bugs
tools: Read, Grep, Bash
model: inherit
---
You are a code reviewer. Read the diff, then …
```

- `name` — имя сабагента (буквы, цифры, `-` и `_`); если его нет — имя файла без `.md`.
- `description` — когда ассистенту стоит поручить задачу этому сабагенту; обязательно.
- Тело после фронтматтера — системный промпт сабагента; обязательно.
- `tools` — имена инструментов, которыми сабагент ограничен: строка через запятую или список YAML.
  Нет поля — доступны все инструменты.
- `model` — модель сабагента. `inherit` и псевдонимы Claude Code (`sonnet`, `opus`, `haiku`) значат
  «модель этого shell»: aish не привязан к одному провайдеру. Любое другое значение — имя модели
  провайдера как есть (`gpt-5`). Нет поля — тоже модель shell.

Остальные поля фронтматтера не читаются. `aish agents` (внутри aish — и просто `agents`) показывает
найденных сабагентов — имя, откуда, модель, инструменты, описание — и проблемы с файлами: битый
фронтматтер, нет `description` или промпта, имя с недопустимыми символами, `name` не совпадает с
именем файла. Файлы без фронтматтера (`README.md` и т. п.) не считаются описаниями и пропускаются.

```
$ aish agents
reviewer  ./.claude  inherit  tools: Read, Grep, Bash  Reviews the diff before a commit and points…
tester    ~/.claude  gpt-5                             Writes tests for the changed code
problem: ~/proj/.claude/agents/draft.md: no description in the frontmatter
```

### Запуск сабагентов

Когда в текущей папке видны сабагенты, у ассистента есть инструмент `task`: он поручает задачу
одному или нескольким сабагентам сразу (`Reviewer, посмотри diff, а tester пусть допишет тесты`).
Сабагенты одного вызова работают параллельно, до четырёх одновременно.

- У каждого свой контекст: он начинает с чистого листа и видит только поручение ассистента и
  инструкции (`CLAUDE.md`), как обычный запрос. Системный промпт — общая часть aish и тело файла
  сабагента вместо `system_prompt` из настроек.
- В сессию попадает только итоговый ответ каждого — результатом вызова `task`. Работа сабагентов
  видна на экране, в панелях (см. ниже).
- bash сабагента исполняется не в твоём shell, а отдельным процессом (`bash -c` или `shell` из
  настроек) в текущей папке и с окружением shell. Поэтому `cd`, `export`, функции из него никуда
  не переносятся, а алиасов и функций shell у сабагента нет.
- Политики действуют те же, а имя сабагента они видят как `context.agent` (см. «Политики»);
  `aish policy --agent ИМЯ ИНСТРУМЕНТ …` спрашивает их о вызове от его имени. Спросить сабагент не
  может, поэтому вердикт «спросить» для него — отказ. Хуки тоже срабатывают, в поле `session` у них
  `sub:ИМЯ`, а `pre-tool` получает имя ещё и в поле `agent`.
- `tools` понимает имена Claude Code и aish без учёта регистра: `Read` — `read_file`, `Write` —
  `write_file`, `Edit` и `MultiEdit` — `edit_file`, `Bash` — `bash` без ограничений, `Skill` — все
  скиллы, которые видит ассистент, `mcp__СЕРВЕР__ИНСТРУМЕНТ` — инструмент MCP `СЕРВЕР_ИНСТРУМЕНТ`,
  `mcp__СЕРВЕР` и `mcp__СЕРВЕР__*` — все инструменты сервера. `Task` пропускается: сабагенты не
  запускают сабагентов. Неизвестное имя ничего не включает; `ask_user` сабагенту не дают.
- `Grep`, `Glob` и `LS` дают bash только для чтения: своих инструментов поиска в aish нет, и сабагент
  ищет командами `grep`, `rg`, `find`, `ls`, `cat`, `head`, `tail`, `wc`. Строка с ними не пишет в
  файлы перенаправлением и не присваивает переменных (можно только в нижнем регистре и локаль:
  `LC_*`, `LANG`, `TZ`); `find` — без `-delete`, `-exec`, `-execdir`, `-ok`, `-okdir`, `-fls` и
  `-fprint*`, `rg` — без `--pre` и `--hostname-bin`, а их слова записаны как есть, без `$`, `$(…)` и
  масок вне кавычек: иначе опция придёт незамеченной.
- `Bash(git diff *)` ограничивает bash сабагента командами по шаблону: каждая простая команда
  строки, включая `$(…)`, `eval` и `bash -c`, должна подойти под один из шаблонов `Bash(…)` или,
  при `Grep`, `Glob`, `LS`, быть командой чтения. `*` — любые символы, `git diff:*` значит
  `git diff *`, шаблоны в одних скобках разделяются запятой: `Bash(git log, git diff)`. Остальные
  команды не исполняются, как и код, собранный во время исполнения (`eval "$x"`, `$cmd`,
  перенаправление в `$file`): его не проверить. Переменные строка задаёт только в нижнем регистре и
  локаль, кроме переменных прокси (`https_proxy` и др.): `PATH=. git log`, `export GIT_DIR=…`,
  `env GIT_SSH_COMMAND=…`, `https_proxy=… git push` и арифметика над переменными
  не исполняются. Если в `tools` есть ещё `Bash` без шаблона, bash не
  ограничен. Шаблоны других инструментов (`Read(src/**)`) не поддерживаются: такая запись не
  включает ничего.
- Сабагент со своей `model`, отличной от модели shell, работает с effort провайдера по умолчанию и
  без автокомпакта: effort и окно контекста shell подобраны под его модель.
- Сабагентов можно запустить в фоне (`background` у `task`): вызов сразу возвращает по строке
  `started bg1 (reviewer)`, и ассистент работает дальше или отвечает тебе, не дожидаясь их.
  - Ответы он забирает сам: `task_wait` ждёт названных (без `ids` — любого) до `timeout` секунд (60,
    не больше 600), `task_result` отдаёт то, что есть, не дожидаясь, а без `ids` — список всех с
    состоянием; `task_cancel` останавливает. В сессию ответ попадает результатом этих вызовов — в
    том же запросе или в одном из следующих.
  - Ctrl+C и конец запроса фоновых не останавливают — только `task_cancel`, `aish clear`, `aish new`,
    `aish resume` и выход из aish. Запрос, после которого они ещё работают, кончается строкой
    `[aish: 2 subagents still running in the background, see aish tasks]`.
  - На экран их работа не выводится, панелей у них нет. `aish tasks` перечисляет фоновых: id,
    сабагент, состояние (`queued`, `running`, `ok`, `error`, `cancelled`) и начало задания;
    `aish tasks show bg1` печатает вывод одного — его вызовы, вывод команд, ответ — каким он есть
    сейчас, у работающего и у законченного. Пока `task_wait` ждёт, его вызов выводит, как команда,
    строку `waiting for bg1, bg2… 12s` (свёрнута, как вывод; видна в Ctrl+O и при `fold_lines` не 0);
    кончилось ожидание — строка уходит, а на её месте ответы. Работают до четырёх одновременно,
    остальные ждут в очереди; незаконченных — не больше восьми, законченных помнится 32 последних.
- Если у тебя есть свой инструмент с именем `task`, он остаётся, а сабагенты ассистенту не
  предлагаются.

### Панели

Пока сабагенты работают, экран занят их панелями, как окнами tmux: по панели на сабагента, в шапке —
номер, имя и состояние (`running`, `ok`, `rc N`, `interrupted`), ниже — конец его вывода. Остальной
вывод — ассистента и shell — в это время копится и появляется, когда экран освобождается.

- `1`…`9` — развернуть панель с этим номером на весь экран, `0` или Esc — обратно к сетке.
- `q` или Ctrl+O — убрать панели и вернуться к обычному экрану; сабагенты продолжают работать, а
  Ctrl+O возвращает панели (не просмотр свёрнутого).
- Ctrl+C прерывает запрос вместе с сабагентами.

Когда закончил последний, экран возвращается, а под вызовом `task` остаётся по строке на сабагента:
`✓ reviewer  (42 lines · ctrl+o to expand)` или `✗ tester  (3 lines · rc 1 · ctrl+o to expand)`.
Полный вывод каждого открывает Ctrl+O, как свёрнутый вывод команд.

## MCP-серверы

Инструменты MCP-серверов называются `<сервер>_<инструмент>`. Модель вызывает их как обычные
инструменты (ниже — как она о них узнаёт), а сам их зовёшь через `aish tool`:
`aish tool github_search_issues "bug" --state open`.
Серверы описываются в `~/.config/aish/mcp.yaml` (путь меняется `mcp_config` в `config.toml`;
нет файла — MCP выключен):

```yaml
servers:
  github:
    command: npx
    args: ["-y", "@modelcontextprotocol/server-github"]
    env:
      GITHUB_TOKEN: ${GITHUB_TOKEN}   # переменные раскрываются
    timeout: 120                      # секунд на вызов, по умолчанию 60
  tracker:
    command: npx
    args: ["-y", "tracker-mcp"]
    env_command:                      # значение — вывод команды
      TRACKER_TOKEN: pass show tracker/token
  remote:
    url: https://example.com/mcp      # Streamable HTTP
    headers:
      Accept-Language: ru
    headers_command:
      Authorization: echo "Bearer $(pass show example.com/token)"
    expose: tools                     # схемы модели сразу; по умолчанию deferred — через tool_search
```

Токен не обязательно держать в файле или экспортировать перед запуском aish: в `env_command` и
`headers_command` значение переменной или заголовка — вывод команды. Она идёт через `sh -c` в `~`, с
окружением aish и без stdin, до 30 секунд; конечный перевод строки отрезается, пустой вывод или
ненулевой код — ошибка старта сервера с концом stderr команды. Команды запускаются при каждом старте
сервера, вывод нигде не хранится, а в ошибках и в `aish mcp` скрыт, какой бы ни был ключ. Сервер с
такими командами при запуске aish в фоне не опрашивается: команды ждут первого обращения — вызова
или `aish tool`. Ключ не может быть сразу в `env` и `env_command` (`headers` и `headers_command`).
`pass` без ключа в кэше gpg-agent и без графического pinentry пароль здесь может не спросить —
разблокируй ключ до запуска aish (хотя бы `pass show … >/dev/null`).

- Сервер запускается при первом вызове и живёт до выхода из shell. Список инструментов кэшируется в
  `~/.cache/aish/mcp/`, поэтому в следующий раз инструменты известны сразу. Сервер, которого нет в кэше,
  опрашивается в фоне при старте; модель увидит его инструменты со следующего запроса, `aish tool`
  дождётся старта.
- Аргументы — как у своих инструментов: обязательные строки и числа позиционно, остальное флагами
  `--name значение`, булевы — `--name`, объекты и массивы — JSON. `aish tool NAME -h` показывает форму.
- Текст идёт в stdout, картинки и бинарные данные — во временный файл, печатается его путь. Ошибка
  инструмента или упавший сервер — ненулевой код возврата и сообщение с концом stderr сервера.
- По умолчанию (`expose: deferred`) схемы MCP-инструментов в запрос не идут: модель видит в системном
  промпте их полные имена по серверам, загружает нужные инструментом `tool_search` — по именам или по
  словам из имени и описания — и дальше вызывает их как обычные инструменты, так что политика видит и
  инструмент, и его сервер; сам `tool_search` для политики — `Action::"call"` на `Tool::"tool_search"`.
  Загруженные остаются в запросе до сводки (`aish compact`, автокомпакт), `clear` или новой сессии.
  `expose: tools` отдаёт схемы сервера сразу, в каждом запросе, — для серверов с парой инструментов.
- Инструкции сервера (`instructions` из ответа на `initialize`) идут в системный промпт разделом
  «MCP Server Instructions», не длиннее 4 КБ на сервер, и кэшируются в `~/.cache/aish/mcp/` вместе со
  списком инструментов.
- `aish mcp` показывает состояние каждого сервера, транспорт, команду или URL (секреты скрыты),
  инструменты и, для упавших, ошибку.
- Поддерживаются только инструменты (без resources, prompts, sampling), транспорты — stdio и
  Streamable HTTP; старый HTTP+SSE не поддерживается.

## Политики

Чтобы запретить `sudo` или спрашивать перед установкой пакетов, язык политик не нужен — хватит
`[policy]` в `config.toml`:

```toml
[policy]
deny = ["sudo *", "rm -rf /", "git push --force*", "git push -f*"]
ask  = ["apt install *", "pacman -S *", "git push*"]
write_outside_home = "deny"      # "allow" | "ask" | "deny"; нет — allow
```

Шаблон сравнивается с каждой простой командой bash-строки — с её argv через пробел, в том числе
внутри конвейеров, `$(...)`, `bash -c '...'` и за `sudo`; программа сравнивается и по имени без пути:
`sudo *` ловит и `/usr/bin/sudo ls`, и `./sudo ls`. Строка, которую не удалось разобрать,
сравнивается целиком, а команды до ошибки — по одной: bash исполняет строки до синтаксической
ошибки, и `echo hi⏎sudo ls⏎echo 'oops` запускает `sudo ls`; ошибка в коде одного `bash -c "'"` не
мешает разобрать остальной. Ошибку в арифметике (`((1 +))`, `$[…]`, `for ((…))`, индекс `a[…]`) и в
`${…}` bash делает при исполнении, а не при разборе, поэтому команды после неё и подстановки внутри неё
(`$(( $(sudo ls) + ))`) шаблоны тоже видят. Строка с командами, собранными во время исполнения (`eval "$x"`, `$cmd`,
`echo … | bash`, `source` — см. `context.dynamic` ниже), тоже сравнивается целиком. Обе спрашивают
`[y/N]`, если задан хоть один шаблон `deny`/`ask` и строку он не запретил: что за ошибкой и что
соберётся при исполнении, шаблоны не видят.
`*` ловит всё, **включая пробелы и `/`**, `?` — один символ, других
спецсимволов нет: `sudo *` ловит `sudo cat /etc/x`, а `rm -rf /` не ловит `rm -rf /tmp/x`.
`X *` совпадает и с голым `X`: `sudo *` ловит и `sudo` без аргументов, и `alias s=sudo`.
`deny` запрещает, `ask` спрашивает Yes/No (стрелки или `y`/`n`, по умолчанию Yes), `write_outside_home` решает за запись вне
`$HOME`: `write_file`, `edit_file` и редиректы bash-команд (`>`, `>>`, `&>`, `<>`); файл редиректа, известный только при
исполнении (`> "$f"`, относительный путь в строке с `cd`), считается записью вне `$HOME`, как и любой `>` в строке,
которую не удалось разобрать. Запись внутри кода, собранного при исполнении (`bash -c "$s"`, `eval "$x"`),
`write_outside_home` не видит: без шаблонов `deny`/`ask` такая строка проходит — спросить о ней можно
любым шаблоном или политикой Cedar на `context.dynamic`. Что правила не назвали — разрешено. Правила и Cedar проверяются
оба, побеждает строгий: deny любого — deny, затем ask. `[policy]` в `.aish.toml` проекта
добавляется к глобальному — проект может только ужесточить. `aish policy` показывает и число
правил.

Каждый вызов инструмента проверяется политиками на [Cedar](https://docs.cedarpolicy.com/) из
`~/.config/aish/policy/*.cedar`. `forbid` возвращается модели с причиной, `forbid` с аннотацией
`@ask("…")` спрашивает тебя Yes/No; `@reason("…")` — текст, который увидят модель и ты. Нет
политик — разрешено всё, кроме `aish trust` и записи в его файл (см. «Настройки проекта»).
Несколько каталогов (`policy_dir` списком или из `.aish.toml`) проверяются по отдельности, каждый —
свой набор с default deny, побеждает строгий.

Что видит политика (principal везде — `Model::"<имя модели>"`):

| инструмент | action | resource | context |
|---|---|---|---|
| `bash` и любой инструмент, который отдаёт команду shell, — на каждую простую команду | `Action::"run"` | `Command::"rm"` (basename) | `program`, `args`, `flags` (`-rf` → `r`, `f`; `--force` → `force`), `operands`, `paths`, `text`, `line`, `cwd`, `home`, `parse_error`, `dynamic` |
| `read_file` / `write_file`, `edit_file` и редиректы `>`, `>>` bash-команды | `Action::"read"` / `Action::"write"` | `File::"/abs/path"` | `path`, `exists`, `cwd`, `home` |
| остальные (внешние, MCP, скиллы) | `Action::"call"` | `Tool::"имя"` | `server`, `path`, `cwd`, `home` |
| вызов сабагента — любой из перечисленных | то же | то же | то же и `agent` — имя сабагента; у вызовов основного агента `agent` нет |

Команды bash-строки разбираются все: конвейеры, `$(...)`, `bash -c '...'` и обёртки — `sudo rm x`
даёт запросы и для `sudo`, и для `rm`; вердикт вызова — худший из них. Обёртки читают свои опции,
как сама программа (значение опции — не команда): `sudo`, `doas`, `run0`, `pkexec`, `su`, `runuser`, `sg`,
`env`, `nice`, `ionice`, `nohup`, `setsid`, `stdbuf`, `time`, `timeout`, `watch`, `flock`, `xargs`, `chroot`,
`unshare`, `nsenter`, `setpriv`, `taskset`, `chrt`, `prlimit`, `setarch`, `systemd-run`, `systemd-inhibit`,
`strace`, `ltrace`, `valgrind`, `gdb`, `firejail`, `fakeroot`, `proxychains4`, `torsocks`, `unbuffer`,
`numactl`, `cgexec`, `chpst`, `caffeinate` и другие. Так же разбирается код,
который строка отдаёт shell: `eval` со статичными аргументами, here-string и here-document для
`bash`/`sh`, `env -S`, значение `alias`, команда `trap`, `bind -x`, `complete -C`, `compgen -C` и
`mapfile -C`, строки `su -c`, `runuser -c`, `flock ФАЙЛ -c`, `script -c`
и `watch`, `sudo -s`/`-i КОМАНДА…` (слова экранированы, как их экранирует sudo), stdin `sudo -s`/`-i` и `doas -s`,
команда окна и `-c` у `tmux` (`new-window`, `split-window`, `run-shell`, `if-shell`…), `#(…)` его форматов,
строка, которую набирает `tmux send-keys` или `screen -X stuff`, команда окна `screen` и `screen -X exec`,
команда `parallel` (`{}` — слово из подстановки), а без команды — значения `:::` и stdin, алиас `!…` из
`git -c alias.ИМЯ=…`. И код строк, которые bash вычисляет сам: индексов в именах-строках (`let 'a[$(…)]=1'`, `unset`,
`test -v`, `[[ -v ]]`, `declare -n`, `read`, `printf -v`), в значениях присваиваний (`x='a[$(…)]'` выполнит
`(( x ))`), в одинарных кавычках арифметики и `"${x:-'…'}"` и в `declare -a a='($(…))'`; индекс с подстановкой
в строке `let` и `test -v` (`let "a[$i]=1"`) — `computed`, а значение не из строки (окружение, файл, `read`,
вывод команды) не видно. Удалённая команда `ssh ХОСТ КОМАНДА…` и stdin голого `ssh ХОСТ` разбираются, как
`bash -c`, но их пути и редиректы —
файлы другой машины: ни в `paths`, ни в `Action::"write"` они не попадают. Чего нельзя знать до
исполнения, помечено
в `context.dynamic` (множество): `computed` — программа или код из подстановок и глобов (`$x`,
`"$(which rm)"`, `eval "$x"`, `bash -c "$x"`, `complete -W '$(…)'`), имя переменной из них (`read "$v"`,
`printf -v "$v"`, `declare -n r="$v"`), код, которого в строке нет (макрос `bind`, команды истории
`fc`, кроме `fc -l`, клавиши `send-keys`, которые правят строку, — `Tab`, `BSpace`, стрелки, — команды
tmux в строке `if-shell`, Perl в `{= =}` у `parallel`), `{}` в кавычках у `parallel`, файл редиректа,
неизвестный до исполнения (`> "$f"`, относительный путь в строке с `cd` или с кодом, который идёт в
другом каталоге: у `tmux`, `screen -X`, алиаса git, `parallel --workdir`), или путь операнда, неизвестный до исполнения: относительный там,
куда строка увела shell, а политика за ней не проследила (`cd -`, `cd "$d"`, `popd`, `cd` в цикле или
функции, `eval 'cd …'`, команда под `sudo -i`), любой в строке, которая присваивает `HOME`, `PWD`,
`OLDPWD` или `CDPATH` (и `unset`, `for HOME in`, `${CDPATH:=…}`), любой под `chroot` и `sudo -R`,
глоб, который ничего не находит в существующем каталоге (строка может сама создать то, что он найдёт),
`**`, extglob; `source` — `source` и `.`, `tmux source-file`, `stdin` — shell читает
команды со stdin (`echo … | bash`, `… | parallel` без команды), `prompt` — присваивание
`PROMPT_COMMAND`, `PS0`, `PS1`, `PS2`,
`PS4`, `BASH_ENV`, `ENV`, `MAILPATH` — не только `=` и `export`, но и `read`, `printf -v`, `mapfile`,
`declare -n`, `rebind` — имя команды начнёт запускать другое: присваивание `PATH` (и
`export PATH=…:$PATH`), `EXECIGNORE`, `BASH_CMDS`, `BASH_ALIASES`, `unset PATH`, `hash -p`, `enable`
(кроме `-n`, `-d` и списка), `git config alias.ИМЯ '!…'` (код алиаса тоже разбирается),
`depth` — вложенность глубже четырёх уровней. Пример спрашивает о любой
пометке; отпустить `source` — `unless { context has dynamic && context.dynamic == ["source"] }`.
Переменная, из которой программы берут команду (`GIT_SSH_COMMAND`, `PAGER`, `EDITOR`, `LESSOPEN`…),
где бы строка её ни присвоила (`X=… cmd`, `export`, `env`, `sudo`, `for`, `${X:=…}`), разбирается как
`bash -c`, из подстановок — `computed`; загрузчики (`LD_PRELOAD`, `PYTHONPATH`, `NODE_OPTIONS`,
`GIT_CONFIG_*`…) — `rebind`, `bind -f` — `computed`.
`paths` — операнды,
похожие на пути, уже абсолютные и с раскрытыми симлинками: `rm -rf ~/`, `rm -rf "$HOME"` и
`rm -rf /home/me/../me/` дают один и тот же `context.home`, и правило одно; `$PWD` раскрывается в
текущий каталог, а `context.cwd` тоже с раскрытыми симлинками, так что `cd .`, `cd "$PWD"` и
`cd <тот же путь>` ловит одно `context.paths == [context.cwd]`. Пути команды берутся оттуда, куда
её привёл `cd` строки: `cd /etc && cp x passwd` даёт `/etc/passwd` (вне исходного каталога путём
считается и голое слово), после `cd /etc;` — и от `/etc`, и от исходного (`cd` мог не сработать);
так же для `env -C` и `sudo -D`. Глоб и `{a,b}` добавляют то, что из них сделает shell:
`rm -rf /hom?/me` — и `/home/me`; слово как написано тоже остаётся в `paths`. `File` лежит в
цепочке `Dir::"/a/b"` → `Dir::"/a"` → `Dir::"/"`; у домашнего каталога есть псевдоним `Dir::"~"`,
у текущего — `Dir::"."`, так что `resource in Dir::"~"` не зависит от машины (симлинк из `~`
наружу туда не попадает). `File` и `Tool` несут аргументы вызова как tags:
`resource.hasTag("private") && resource.getTag("private") == "false"` (не-строки — компактный JSON).
Для MCP-инструмента `Tool` лежит в `Server::"<сервер>"`.

`context.agent` — имя сабагента, который делает вызов (см. «Сабагенты»); у вызовов основного
агента его нет, поэтому перед сравнением нужен `context has agent`. Сабагенту `reviewer` — только
чтение:

```cedar
@reason("reviewer only reads")
forbid(principal, action == Action::"write", resource)
when { context has agent && context.agent == "reviewer" };

@reason("reviewer only reads")
forbid(principal, action == Action::"run", resource)
when { context has agent && context.agent == "reviewer" &&
       !["cat", "grep", "head", "ls", "rg"].contains(context.program) };
```

Первое правило ловит и `write_file`, и редирект `>` в команде сабагента, второе — любую простую
команду, кроме перечисленных, в том числе внутри `$(...)` и конвейера.

Cedar — default deny: без `permit` запрещено всё, поэтому пример начинается с
`permit(principal, action, resource);` и дальше только запрещает. Движок fail-closed: ошибка
вычисления, отсутствие подходящего `permit` и файл `*.rego` в каталоге — это deny или ошибка
загрузки, а не разрешение. Политики проверяются по схеме при загрузке: опечатка в имени атрибута
(`context.comands`) — ошибка сразу, а не правило, которое молча не срабатывает.

`aish policy` загружает политики и печатает их число (или ошибку валидации);
`aish policy bash 'sudo ls'`, `aish policy write_file /etc/hosts` — спросить их об одном вызове без
модели, аргументы как у `aish tool`. Та же строка о политиках, с правилами `[policy]` или ошибкой
загрузки, стоит в `aish status`.

Пример `examples/policy/default.cedar` запрещает `sudo`, `rm -rf` (и `--recursive`) для `/` и
`$HOME`, `git push --force` и `git push` с `+refspec`, `exit`/`exec`/`logout`, запись вне `$HOME` и
спрашивает перед установкой пакетов.

## Хуки

Хук — исполняемый файл в `~/.config/aish/hooks/<событие>/` (каталог задаёт `hooks_dir` в
`config.toml`). На событие агента aish запускает хуки этого события по порядку имён, даёт каждому
на stdin JSON и читает ответ: JSON-объект или пустой stdout — ничего не менять. Как в Claude Code,
только без регистрации: положил файл с `chmod +x` — он работает со следующего запроса.

| событие | когда | вход (и везде `event`, `cwd`, `session`) | ответ |
|---|---|---|---|
| `user-prompt` | запрос, до модели | `prompt` | `{"context": "…"}` — дописать к запросу: модель получит текст вместе с ним, с маскировкой секретов, как у вывода команд, а журнал хранит его отдельной записью, и `aish session show` его не печатает; `{"deny": "причина"}` — отклонить: запрос не уйдёт модели и не попадёт в журнал |
| `pre-tool` | вызов инструмента, после политики | что видит политика: `tool`, `args`, `line` (строка, отданная shell), `commands`, `parse_error`, `dynamic`, `path`, `home`, `server`, `model`, `agent` (имя сабагента, у основного агента нет); `policy` — её вердикт, `{"action", "reason"}` | `{"action": "allow\|deny\|ask", "reason": "…"}`; `{"args": {…}}` — подменить аргументы |
| `post-tool` | результат инструмента, до записи | `tool`, `args`, `output`, `is_error` | `{"output": "…"}` — заменить результат |
| `stop` | запрос закончен | `text` — последний ответ, `steps`, `input_tokens`, `cached_tokens`, `output_tokens` | ничего, stdout не читается |

```sh
#!/bin/sh
# ~/.config/aish/hooks/pre-tool/no-sudo: ненулевой код — deny, stderr — причина
if grep -q sudo; then echo "sudo — только руками" >&2; exit 1; fi
```

```sh
#!/bin/sh
# ~/.config/aish/hooks/user-prompt/git-status: состояние репозитория к каждому запросу
s=$(git status --short --branch 2>/dev/null) || exit 0
jq -n --arg s "$s" '{context: ("git status:\n" + $s)}'
```

- **Политика — жёсткий дефолт, хук только ужесточает.** `pre-tool` идёт после политики; вызов,
  который она запретила, хуки не видят, а `allow` хука не отменяет её `ask`. Ненулевой код
  возврата `pre-tool` — deny с stderr в качестве причины: её видят и ты (`✗ denied by hook
  no-sudo: …`), и модель. Подменённые `args` получает следующий хук, и политика проверяет их
  заново — из двух вердиктов берётся строгий; в терминале команда уже подменённая.
- Хуки одного события идут друг за другом: `output` одного `post-tool` — вход следующего, первый
  deny останавливает остальные. Хуки проекта (`hooks_dir` в `.aish.toml`, относительно файла,
  например `.aish/hooks`) идут после личных и только после `aish trust` (см. «Настройки проекта»).
- `post-tool` для `bash` срабатывает, когда вывод пришёл от shell; `output` — то, что получит
  модель, со строкой `[exit N, cwd …]`. Терминал показывает вывод как был и под ним строку
  `(the model gets the result as post-tool/… left it)`.
- Хук запускается в каталоге и с окружением shell (экспортированные переменные видны), в своей
  группе процессов. На хук 5 секунд: дольше — группа убивается, запрос идёт дальше. Ошибка хука
  (не запустился, таймаут, ненулевой код у других событий, ответ не JSON или с незнакомым ключом)
  — dim-строка в терминале, хук пропускается, запрос не падает. Если `pre-tool` — охрана,
  `hooks_fail = "deny"` в `config.toml` превращает такую ошибку в запрет вызова (`hook failed: …`),
  как у политики. Ctrl+C обрывает и хук.
- Каталоги читаются один раз на запрос. Файл без `+x` и каталог, названный не по событию, тоже
  дают dim-строку: охранник, который молча не запускается, хуже. Файлы прямо в `hooks/` (общие
  библиотеки хуков) и скрытые пропускаются.
- `aish hooks` (внутри aish — и просто `hooks`) показывает, какие хуки сработают в этом каталоге,
  по событиям и в порядке запуска, и те же проблемы; хуки недоверенного `.aish.toml` в список не
  входят, вместо них — строка с подсказкой `aish trust`. В `aish status` — их число в строке `hooks`.

Пример `examples/hooks/post-tool/mask-secrets` (нужен `jq`) прячет в результатах ключи AWS
(`AKIA…`) и токены GitHub (`ghp_…`). Встроенная маскировка (`mask_defaults`) и так прячет их от
модели при отправке; хук не пускает их и в журнал сессии — и это место для своих правил.

## Настройки

`~/.config/aish/config.toml` (путь — `$AISH_CONFIG`), все ключи необязательны:

```toml
provider = "anthropic"            # или "openai" (Chat Completions), "openai-responses" (Responses API)
base_url = "http://127.0.0.1:8317" # прокси, например cliproxyapi; нет — официальный API провайдера
api_key_env = "AISH_API_KEY"
api_key = ""                      # сам ключ вместо api_key_env; в файле его лучше не держать
http_proxy = "http://127.0.0.1:8080"  # прокси запросов к модели (см. ниже); ни одного ключа — из окружения
https_proxy = "http://127.0.0.1:8080" # то же для https://
all_proxy = "socks5://127.0.0.1:1080" # запасной для схемы без своего; схемы — http, https, socks5, socks5h
no_proxy = "localhost,.corp.example,10.0.0.0/8" # мимо прокси: хосты, домены, CIDR
model = "claude-opus-5"           # или $AISH_MODEL
effort = "high"                   # low … max (у OpenAI ещё none, minimal); нет — уровень модели; или $AISH_EFFORT
max_tokens = 0                    # лимит ответа; 0 — 32000, на effort xhigh/max — 64000
profile = "work"                  # профиль [profiles.work] поверх ключей выше (см. ниже); или $AISH_PROFILE
max_steps = 50                    # шагов агента на один запрос; 0 — без ограничения
max_output_bytes = 16000          # сколько вывода команды видит LLM (голова + хвост); 0 — весь
mask = ["corp-[0-9a-f]{32}"]      # свои регулярки секретов, которые LLM видит как corp***; группа прячет только себя
mask_defaults = true              # встроенные регулярки (AWS, GitHub, OpenAI, Slack, PRIVATE KEY, password=…)
fold_lines = 0                    # сколько строк вывода агента показывать до сворачивания (-1 — не сворачивать)
journal_ignore = ["*secret*", "env", "printenv", "cat *credentials*", "history"]  # команды без вывода в журнале
state_ignore = ["*TOKEN*", "*SECRET*", "*KEY*", "*PASSWORD*", "AWS_*"]            # переменные вне <id>.state
markdown = true                   # рендерить ответы как markdown (false — как есть)
code_style = "monokai"            # стиль подсветки кода: https://xyproto.github.io/splash/docs/
prompt_status = true              # статус контекста справа от промпта
context_window = 0                # размер окна модели в токенах; 0 — узнать у API
compact_at = 0.8                  # доля окна, за которой сессия сжимается в сводку сама; 0 — никогда
sessions_dir = "~/.local/share/aish/sessions" # сохранённые сессии, см. «Сессии»
sessions_ttl = "0"                # удалять при запуске сессии старше: "30d" или "720h"; "0" — не удалять
mcp_config = "~/.config/aish/mcp.yaml"
policy_dir = "~/.config/aish/policy" # политики Cedar, см. «Политики»
hooks_dir = "~/.config/aish/hooks" # хуки, см. «Хуки»
hooks_fail = "allow"              # pre-tool хук упал или завис: "allow" — вызов идёт, "deny" — запрет
tools_dir = "~/.config/aish/tools" # свои инструменты, см. «Свои инструменты»
shell = "/opt/bash/bin/bash"      # какой bash запускать; нет — $SHELL, если это bash, иначе первый bash в PATH
system_prompt = "Дополнение к системному промпту"

[route]                           # что уходит ассистенту, см. «Команда или вопрос?»
capital = true                    # строка с заглавной буквы, не команда
not_found = true                  # слова, а не shell: то, на что bash ответил бы command not found
suffix = "?"                      # строка, которая кончается на suffix; "" — правило выключено
min_words = 2                     # сколько слов нужно для not_found
expand = true                     # раскрывать $VAR и $(…) в запросе

[policy]                          # простые правила рядом с Cedar, см. «Политики»
deny = ["sudo *", "rm -rf /"]     # запретить; * ловит всё, включая пробелы и /
ask = ["git push*"]               # спросить Yes/No
write_outside_home = "ask"        # write_file и edit_file вне $HOME: "allow" | "ask" | "deny"

[profiles.work]                   # профиль, который выбирает profile: endpoint и модель поверх ключей выше, см. ниже
base_url = "http://127.0.0.1:8317"
model = "claude-opus-5"
```

Провайдер — это протокол API. `openai` (Chat Completions) понимают и совместимые серверы —
Ollama, vLLM, LM Studio (`base_url` можно без `/v1`), но рассуждения модели между ходами он
теряет. `openai-responses` — Responses API OpenAI для моделей с рассуждением (gpt-5, o-серия):
рассуждения приходят зашифрованными, лежат в журнале и уходят обратно со следующим ходом, как
thinking-блоки у `anthropic`; у OpenAI при этом ничего не хранится (`store: false`). Ключ, если
нет ни `api_key`, ни переменной из `api_key_env`, берётся из переменной провайдера:
`ANTHROPIC_API_KEY` или `OPENAI_API_KEY`.

`http_proxy`, `https_proxy`, `all_proxy` и `no_proxy` — прокси запросов к модели, как у curl:
`http_proxy` для `http://`, `https_proxy` для `https://`, `all_proxy` — для схемы, у которой своего
нет (пустое значение — как незаданное), `no_proxy` — мимо прокси (`*` — всё мимо), loopback не
проксируется никогда. Если задан хоть один из четырёх, переменные окружения (`http_proxy`,
`HTTPS_PROXY` и прочие, с которыми запущен aish) не читаются вовсе; не задан ни один — работают
они, как раньше. `all_proxy` (socks5) из окружения aish не берёт, из `config.toml` — берёт. Ключи
можно задать и в профиле — или выключить там: `http_proxy = ""` (и `all_proxy = ""`, если он задан
сверху) или `no_proxy = "*"` для локальной Ollama; незаданные профиль берёт у верхнего уровня.
MCP-серверов ключи не касаются: их запросы идут по окружению aish.

Профили — несколько endpoint'ов в одном файле: рабочий прокси, личный ключ, локальная Ollama.
Таблица `[profiles.ИМЯ]` накладывается на верхний уровень, а не заменяет его: незаданные в ней
ключи берутся оттуда, пустая таблица — сам верхний уровень. Кроме ключа API: свой `api_key` или
`api_key_env` в профиле заменяет оба ключа верхнего уровня, а профиль, который задаёт `provider`
или `base_url`, но не ключ, берёт его из переменной провайдера — ключ одного endpoint'а не уходит
на другой. И кроме effort, если провайдер профиля другой (пустой `provider` — `anthropic`): без
своего `effort` такой профиль берёт уровень провайдера по умолчанию — уровня одного провайдера у
другого может не быть. Профиль наследует прокси верхнего уровня, и тот, что задаёт свой `base_url`:
прокси — свойство сети, а не endpoint'а. В профиле бывают `provider`,
`base_url`, `api_key`, `api_key_env`, `http_proxy`, `https_proxy`, `all_proxy`, `no_proxy`, `model`,
`effort`, `max_tokens` и `context_window`. Действует
профиль из `$AISH_PROFILE`, иначе из `profile`; нет ни того, ни другого — только верхний уровень,
как в конфиге без профилей. `$AISH_MODEL` и `$AISH_EFFORT` — поверх выбранного профиля. В shell
профиль переключает `aish model ИМЯ` (см. «Контекст и модель»).

```toml
profile = "work"

[profiles.work]
provider = "anthropic"
base_url = "http://127.0.0.1:8317"
api_key_env = "AISH_API_KEY"
model = "claude-opus-5"

[profiles.local]
provider = "openai"
base_url = "http://localhost:11434"
model = "qwen3:32b"
context_window = 32000            # Ollama не сообщает размер окна
```

Опечатка в имени ключа (и внутри `[profiles.ИМЯ]`), неизвестный профиль или отрицательный лимит —
ошибка при запуске с указанием ключа и файла, а не молчаливое значение по умолчанию.

Файлы настроек — `config.toml` со всеми профилями, `.aish.toml` проектов и политики из `policy_dir` —
aish читает при запуске и потом только по команде `aish apply-config`: правка действует вся сразу и
тогда, когда ты скажешь, а не один ключ со следующего запроса, другой — после перезапуска. Пока она
не применена, запросы идут со старыми настройками, а первый запрос после правки пишет
`[aish: config changed on disk: aish apply-config to apply it]`. `aish apply-config` перечитывает
`config.toml`, `.aish.toml` текущего каталога и политики и проверяет их: сломанный файл — ошибка, и
ничего не меняется; иначе печатает изменившиеся ключи и файлы. Профиль, модель и effort shell'а
следуют правке, пока они те, что дал `config.toml`; выбранное `aish model` остаётся. Профиль shell'а,
который из `config.toml` убрали или переименовали, `aish apply-config` заменяет на выбранный там и
пишет об этом. Только перезапуск aish применяет `shell`, `[route]`, `sessions_dir`, `sessions_ttl`,
`mcp_config` и правку самого файла MCP-серверов — `aish apply-config` их называет. Переменные
окружения shell (`$AISH_PROFILE`, `$AISH_MODEL`, `$AISH_EFFORT`, ключи API) по-прежнему читаются на
каждый запрос, каталоги инструментов, хуков, скиллов и сабагентов — тоже: это код, а не настройки.

### Настройки проекта

В репозитории может лежать `.aish.toml` — он накладывается на `config.toml` для запросов из
этого репозитория. Файл ищется от текущего каталога вверх: берётся ближайший, но не выше корня
git-репозитория (каталога с `.git`) и не в `~` — домашний каталог не проект, для него есть
`config.toml`. Ищется по каталогу shell: `cd` в другой репозиторий — другие настройки; файл
каталога читается при первом запросе оттуда, новый или исправленный действует после
`aish apply-config`. `aish status` показывает оба файла в строке `config`; `aish tool` видит инструменты
проекта.

Разрешены только ключи, которые не тратят чужие деньги и не уводят трафик: `system_prompt`,
`max_steps`, `max_output_bytes`, `fold_lines`, `markdown`, `code_style`, `policy_dir`, `[policy]`
(списки складываются с глобальными, из двух `write_outside_home` берётся строгий), `tools_dir`,
`hooks_dir` (см. «Хуки»).
`system_prompt` **дописывается** к глобальному, `policy_dir` и `tools_dir` **добавляются** к
глобальным каталогам (каждый каталог политик — свой набор Cedar, вызов должен пройти все; `permit`
проекта не разрешает то, что не разрешили твои политики, а каталогу проекта из одних `forbid` нужен
свой `permit(principal, action, resource);`; инструмент проекта с именем личного
пропускается), относительные пути — от каталога с `.aish.toml`; остальные ключи заменяют значение.
`provider`, `base_url`, `api_key*`, `http_proxy`, `https_proxy`, `all_proxy`, `no_proxy`, `model`,
`effort`, `max_tokens`, `shell`, `sessions_dir`,
`mcp_config`, `context_window`, `profile` и `[profiles.*]` в `.aish.toml` запрещены: склонированный
репозиторий не должен выбирать, куда и за чей счёт уходят запросы. Запрещённый или незнакомый
ключ — ошибка с именем ключа и файла, запрос не выполняется.

```toml
# .aish.toml в корне репозитория
system_prompt = "Это Go-сервис; тесты гонять через make test, не go test."
tools_dir = "tools/aish"       # относительно этого файла
policy_dir = ".aish-policy"
max_output_bytes = 32000
```

`hooks_dir` и `tools_dir` запускают код из самого репозитория, поэтому действуют, только когда ты
доверился файлу: `aish trust` в каталоге проекта печатает путь к `.aish.toml` и эти ключи и
запоминает sha256 файла и этих каталогов (`~/.local/share/aish/trusted.json`). До этого
остальные ключи работают, а эти два пропускаются: на первом запросе — dim-строка `aish: … sets
hooks_dir; … until you run aish trust`, в `aish status` — пометка `(untrusted: …)`. Доверие
снимает любая правка `.aish.toml`, хуков и инструментов проекта, новый файл тоже, до нового `aish trust`;
снимает сразу, не дожидаясь `aish apply-config`, а исправленный и снова доверенный файл действует после него.
`aish trust --revoke` забывает файл, `aish trust --list` показывает доверенные и помечает
изменившиеся с тех пор. Команда набирается только как `aish trust`: `trust` без `aish` — это p11-kit.
`aish trust` — только для пользователя: команду ассистента с ним (кроме `--list`) и запись в
`trusted.json` aish отклоняет при любых политиках.

## Как это устроено

```
терминал ⇄ aish (PTY-прокси, журнал сессии, агент: LLM, инструменты, политики; unix-сокет $AISH_SOCK)
               ⇅ байты насквозь; маркеры OSC 6973 вырезаются
           bash --rcfile <rc>     rc = source ~/.bashrc + init.bash
               Enter → bind -x __aish_route → текст: строка → __aish_ask '…'
                                              ⇅ JSON-RPC
                         aish agent start/resume (передаёт запрос агенту в прокси и ждёт)
```

aish — прокси между терминалом и bash: байты идут насквозь, а служебные маркеры, которые печатает
`init.bash`, вырезаются. По ним прокси знает, где начался и закончился вывод каждой команды, и пишет
его в журнал, очищенным от ANSI; вывод полноэкранных программ (vim, htop) не сохраняется. Enter
перехватывает `bind -x`: строка либо уходит bash как есть, либо превращается в `__aish_ask '…'`,
которая передаёт запрос агенту. Агент живёт в самом прокси, вместе с журналом, политиками и
MCP-серверами, поэтому шаг не зависит от размера сессии; `aish agent start` в shell лишь держит
соединение, пока прокси работает, — `Ctrl+C` по нему и останавливает агента. Команду `bash` агента
исполняет та же `__aish_ask` через `eval` в текущем shell — поэтому `cd` и `export` сохраняются.
Подробнее — в `CLAUDE.md`.
