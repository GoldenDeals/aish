# Шина событий: как пользоваться

Ядро — средство общения модулей. Модули ничего не знают друг о друге: они подписываются на события
и отправляют события. Ядро гарантирует, что каждое внешнее событие обрабатывается атомарно:
либо все его последствия применились, либо ни одно (A и C из ACID; I и D не нужны — всё в памяти,
и незакоммиченная транзакция всегда одна).

Публичный контракт — `pkg/` (`bus`, `tx`, `event`). Реализация — `internal/core/...`, модули её не импортируют.

## Модель

- **Событие первого порядка** приходит через `Bus.Dispatch` и открывает **новую транзакцию** (tx).
  Что считать внешним, решает модуль, а не ядро: событие одно и то же, разница только в точке входа.
- **Внутренние события** отправляются через `tx.Emit` из sync-обработчиков и остаются в той же tx.
- Tx — это **шаг**, а не весь диалог: например, «сообщение пользователя», «tool call модели»,
  «ответ тула» — отдельные tx. Модуль заканчивает шаг тем, что делает долгую работу в async-обработчике
  и отправляет результат новым `Dispatch`.
- В каждый момент открыта **одна** tx. Следующий `Dispatch` ждёт, пока предыдущая закоммитится или откатится.
- Tx **коммитится**, когда все sync-обработчики всех её событий вернули `nil` и все отправленные в ней стримы
  финализированы. Tx **откатывается** при первой ошибке или панике обработчика либо по окончании ctx у `Dispatch`.

| | sync | async |
|---|---|---|
| Подписка | `SubscribeSync(priority, f, h)` / `bus.Sync[T]` | `SubscribeAsync(f, h)` / `bus.Async[T]` |
| Когда вызывается | сразу при `Emit`, в горутине отправителя | после коммита, каждый в своей горутине |
| Порядок | priority по убыванию, при равном — порядок подписки | не гарантирован |
| Tx его ждёт | да | нет |
| Ошибка / паника | откатывает tx | ошибку вернуть некуда; паника роняет процесс |
| Получает | все события tx | только события закоммиченных tx, доставку которых не остановили |

## Быстрый старт

Шину модуль получает в `Init`; как написать и подключить модуль — [modules.md](modules.md).

```go
import (
	"github.com/GoldenDeals/aish-core/pkg/bus"
	"github.com/GoldenDeals/aish-core/pkg/event"
	"github.com/GoldenDeals/aish-core/pkg/tx"
)

// В Init(b bus.Bus, cfg config.Config): подписки.
bus.Sync(b, 0, event.ByName("user.message"), func(ctx context.Context, t tx.Tx, ev event.Event[string]) error {
	history = append(history, ev.Data())
	t.OnAbort(func() { history = history[:len(history)-1] })
	return t.Emit(ctx, event.New("history.updated", len(history)))
})

// В Start и позже: события первого порядка.
err := b.Dispatch(ctx, event.New("user.message", "привет")) // nil — закоммичено, иначе причина отката
```

## События

```go
ev := event.New("tool.call", ToolCall{ID: 7, Name: "ls"}) // event.Event[ToolCall], неизменяемое
ev.Name()                                                // "tool.call"
ev.Data()                                                // ToolCall{...}
```

- `event.Any` (только `Name()`) — то, с чем работает ядро; любое `Event[T]` ему удовлетворяет.
- `event.Filter` — `func(event.Any) bool`; готовый — `event.ByName(name)`.
- Типизированные подписки `bus.Sync[T]` / `bus.Async[T]` отдают обработчику `event.Event[T]`.
  Событие с подходящим именем, но **другим типом данных** они молча пропускают.
- Свой тип события тоже подойдёт: достаточно методов `Name()` и `Data()`.

## Sync-обработчики

```go
type SyncHandler func(ctx context.Context, tx tx.Tx, ev event.Any) error
```

- **Порядок.** Чем больше priority, тем раньше. Держи приоритеты именованными константами в одном месте:
  перехват и `EmitIn` опираются на чужие числа.
- **`tx.Emit(ctx, ev)`** синхронно прогоняет sync-обработчики нового события и возвращается, когда они закончили.
  Передавай ctx, полученный обработчиком: чужой ctx ядро заменит своим.
- **`tx.EmitIn(ctx, ev, lo, hi)`** — то же, но только для sync-обработчиков с `lo <= priority <= hi`
  (равный: `p, p`; от: `p, math.MaxInt`; до: `math.MinInt, p`). Async-подписчиков диапазон не фильтрует.
  `lo > hi` — паника, то есть откат.
- **Ошибка** (кроме `bus.Stop`) или **паника** откатывает всю tx. Ошибка возвращается и из `Emit` у отправителя,
  но проглотить её нельзя: tx уже откатывается, дальнейшие `Emit` вернут `tx.ErrClosed`.
- **`tx.OnAbort(f)`** — откат своего состояния. Регистрируй сразу после изменения. При откате функции
  вызываются в обратном порядке, до начала следующей tx.
- **ctx заканчивается вместе с tx**, в том числе при коммите. Работа, которая должна пережить tx, —
  через `context.WithoutCancel(ctx)` или async-подписку.
- **Состояние, которое трогают только sync-обработчики, не требует мьютексов:** tx идут по одной,
  sync-обработчики — последовательно. Условие: `Tx` вызывается только из горутины обработчика.
- **Побочные эффекты наружу** (ответ пользователю, запись в файл, HTTP) — только в async: их нельзя откатить.

## Async-обработчики

```go
type AsyncHandler func(ctx context.Context, ev event.Any)
```

- Вызываются после коммита, для каждого незадержанного события tx. Порядок не гарантирован, tx их не ждёт.
- ctx не отменяется, когда `Dispatch` вернулся (это ctx `Dispatch` без отмены).
- Могут вызывать `b.Dispatch` — так долгая работа (вызов LLM, запуск тула) превращается в следующий шаг.
- Работают параллельно со следующей tx: опирайся на данные события, а не на чужое состояние.

## Как проходит tx

Что происходит внутри `Dispatch` (реализация — `internal/core/bus`, `internal/core/tx`):

1. **Очередь.** ctx принадлежит текущей tx — сразу `bus.ErrNestedTx`. Иначе `Dispatch` ждёт, пока освободится
   очередь (одна tx за раз). ctx закончился в очереди — возвращается его причина: tx не открывалась,
   событие никто не видел, откатывать нечего.
2. **Открытие.** tx получает новый `ID()` и свой ctx — дочерний от ctx `Dispatch`. Его и получают
   sync-обработчики. Состояние tx хранится в причине отмены этого ctx: нет причины — tx жива,
   ошибка — откатывается, `tx.ErrClosed` — закрыта.
3. **Доставка.** Событие первого порядка проходит тот же путь, что и любой `Emit`:
   - tx не жива — `tx.ErrClosed`, никто не вызывается;
   - снимается список подписчиков (sync — по priority, async — все), событие пишется в **журнал** tx.
     Подписки и отписки после этого момента на это событие не влияют;
   - sync-обработчики из диапазона `[lo, hi]` вызываются по очереди: фильтр, затем обработчик;
   - после каждого из них:
     - ошибка (кроме `bus.Stop`) или паника — tx откатывается с этой причиной, остальные не вызываются,
       ошибка возвращается отправителю;
     - tx стала откатываться, пока обработчик работал (дедлайн, проглоченная ошибка вложенного `Emit`), —
       остальные не вызываются, что бы обработчик ни вернул, даже `bus.Stop`;
     - `bus.Stop` — событие помечено задержанным, остальные не вызываются, отправителю возвращается `nil`.
4. **Стримы.** Когда цепочка доставки вернулась целиком, ядро по очереди ждёт финализации каждого стрима
   из журнала — **включая задержанные**. Ждёт с ctx tx, поэтому дедлайн `Dispatch` откатывает tx.
5. **Итог.**
   - **Откат** (была причина): `OnAbort` в обратном порядке регистрации; паника в одной из них не мешает
     остальным и добавляется к ошибке. `Dispatch` возвращает причину. Async не получают ничего.
   - **Коммит**: ctx tx отменяется с `tx.ErrClosed` — ctx sync-обработчиков закончились. Для каждого
     незадержанного события журнала и каждого async-подписчика, снятого на шаге 3, запускается горутина:
     фильтр, затем обработчик с ctx `Dispatch` без отмены. `Dispatch` возвращает `nil`, не дожидаясь их.
6. **Выход.** Очередь освобождается, и только теперь может начаться следующая tx. Поэтому `OnAbort`
   всегда успевают до неё, а async-обработчики — нет.

`Emit` вызывает обработчики нового события **сразу и до конца** — в глубину, внутри текущего обработчика:

```
Dispatch(A)
├─ A: sync p=10 ── Emit(B) ─┬─ B: sync p=5
│                           └─ B: sync p=0
├─ A: sync p=0                                  ← B уже обработано целиком
├─ ждём стримы журнала [A, B]
└─ коммит → go async(A), go async(B)            ← или откат → OnAbort в обратном порядке
```

## Перехват: задержать и отпустить

Модуль с высоким priority возвращает `bus.Stop` — событие задержано: младшие priority и async его не получат,
tx при этом коммитится. Отпускает он его в **следующей** tx через `EmitIn` ниже своего priority.

Как это выглядит по шагам (перехватчик — `p=1000`, исполнитель — `p=0`, аудит — `p=2000`):

```
tx1: Dispatch(tool.call)
     p=2000 аудит        получает tool.call
     p=1000 перехватчик  кладёт в pending, Emit(permission.request), возвращает Stop
     p=0    исполнитель  не вызывается
     коммит → async получают permission.request, но не tool.call

tx2: Dispatch(permission.response)
     p=1000 перехватчик  EmitIn(tool.call, math.MinInt, 999)
            p=2000 аудит        вне диапазона — второй раз не получает
            p=1000 перехватчик  вне диапазона — не перехватывает снова
            p=0    исполнитель  получает
     коммит → async получают permission.response и tool.call
```

- `bus.Stop` действует на одну доставку одного события: тот, кто сделал `Emit`, получает `nil`, tx идёт дальше,
  другие события tx не задеты.
- Кто старше перехватчика (и с тем же priority, но подписан раньше), событие уже получил. Диапазон
  `hi = P-1` при отпускании нужен, чтобы им не доставить его второй раз, а перехватчику — не задержать снова.
- Отпущенное событие — новая запись в журнале tx2: подписчики снимаются заново, async получат его после
  коммита tx2. Откатится tx2 — откатятся и последствия отпускания, поэтому перехватчик в `OnAbort`
  возвращает событие в `pending`.
- Откатится tx1 — задержка ничего не значит, событие больше никто не увидит; `OnAbort` убирает его из `pending`.
- Задержанный стрим всё равно держит коммит tx1 до своей финализации.

Пример: спросить пользователя, разрешить ли тул.

```go
const PrioPermission = 1000

pending := map[int]event.Any{} // трогают только sync-обработчики — мьютекс не нужен

bus.Sync(b, PrioPermission, event.ByName("tool.call"), func(ctx context.Context, t tx.Tx, ev event.Event[ToolCall]) error {
	id := ev.Data().ID
	pending[id] = ev
	t.OnAbort(func() { delete(pending, id) })
	if err := t.Emit(ctx, event.New("permission.request", id)); err != nil {
		return err
	}
	return bus.Stop
})

// UI: async, после коммита tx1. Ответ пользователя — внешнее событие, новая tx.
bus.Async(b, event.ByName("permission.request"), func(ctx context.Context, ev event.Event[int]) {
	allowed := askUser(ev.Data())
	_ = b.Dispatch(ctx, event.New("permission.response", Answer{ID: ev.Data(), Allowed: allowed}))
})

bus.Sync(b, PrioPermission, event.ByName("permission.response"), func(ctx context.Context, t tx.Tx, ev event.Event[Answer]) error {
	id := ev.Data().ID
	held, ok := pending[id]
	if !ok {
		return nil
	}
	delete(pending, id)
	t.OnAbort(func() { pending[id] = held })
	if !ev.Data().Allowed {
		return t.Emit(ctx, event.New("tool.denied", id))
	}
	return t.EmitIn(ctx, held, math.MinInt, PrioPermission-1)
})
```

Почему не ждать ответа прямо в обработчике: ответ придёт через `Dispatch`, а он ждёт текущую tx,
которая ждёт обработчик — вечное ожидание, и вся шина стоит.

Ограничение: у перехватчика должен быть **уникальный** priority среди подписчиков этого события —
соседи с тем же priority, подписанные позже, не получат событие ни при задержке, ни при отпускании.

## Стримы

Стрим — событие, данные которого ещё поступают из канала отправителя. Закрытие канала финализирует стрим.

```go
ch := make(chan string)
go func() { // отдельная горутина, запущенная ДО Dispatch/Emit
	defer close(ch)
	for tok := range generate(ctx, prompt) {
		ch <- tok
	}
}()
err := b.Dispatch(ctx, event.NewStream("llm.answer", ch))
```

- `event.Stream[T]` — это `event.Event[[]T]`: `Data()` отдаёт копию уже полученных чанков (после финализации — все).
- `Read(ctx)` — новая копия потока с самого начала, канал закрывается после финализации.
- `Finalized()` / `event.Finalized(ev)` — закрыт ли канал отправителя (обычные события финализированы всегда).
- `Wait(ctx)` — дождаться финализации.
- **Коммит ждёт финализации всех стримов tx.** Не закрыл канал — tx откатится по дедлайну `Dispatch`.

Подписчики:

```go
// Показ на экране: читать в своей горутине и сразу вернуть nil.
bus.Sync(b, PrioUI, event.ByName("llm.answer"), func(ctx context.Context, _ tx.Tx, ev event.Event[[]string]) error {
	s := ev.(event.Stream[string])
	go func() {
		for tok := range s.Read(context.WithoutCancel(ctx)) { // ctx tx закончится на коммите, а дочитать надо
			printToken(tok)
		}
	}()
	return nil
})

// Состояние: дождаться конца прямо в обработчике и записать атомарно с tx.
bus.Sync(b, PrioHistory, event.ByName("llm.answer"), func(ctx context.Context, t tx.Tx, ev event.Event[[]string]) error {
	s := ev.(event.Stream[string])
	if err := s.Wait(ctx); err != nil {
		return err
	}
	history = append(history, strings.Join(s.Data(), ""))
	t.OnAbort(func() { history = history[:len(history)-1] })
	return nil
})
```

- Если писатель — сам обработчик, который пишет в канал **после** `Emit` в своей же горутине, то подписчик,
  читающий стрим прямо в обработчике, ждёт вечно. Писатель — всегда отдельная горутина.
- Обработчик, ждущий конца стрима, держит sync-цепочку: младшие priority получат событие только после конца.
  Поэтому живой показ должен иметь priority выше, чем такие обработчики.
- Async-подписчики получают стрим уже финализированным: `Data()` возвращает всё.

## Пример целиком: `modules/llm/anthropic`

Один ответ модели — цепочка из нескольких tx. Контекст сессии (`m.system`, `m.dialog`) меняют только
sync-обработчики с priority `math.MinInt` — после всех остальных; запрос к API идёт в async, вне tx.

```
tx1  Dispatch(user.message)                                  ← UI
     p=100     инжектор   Emit(llm.system) ─ addSystem: m.system += фрагмент, OnAbort
     MinInt    addUser    m.dialog += сообщение, OnAbort
                          Emit(anthropic.request{снимок system и dialog})
     коммит → go ask(anthropic.request)

ask  (async, вне tx)      запрос к API; ошибка до первого чанка → Dispatch(llm.error)
                          писатель стрима — отдельная горутина, запущенная до Dispatch

tx2  Dispatch(llm.answer)                                    ← ask
     p>MinInt  UI         читает стрим в своей горутине, сразу возвращает nil
     MinInt    addAnswer  Wait — ждёт конца стрима; m.dialog += ответ, OnAbort
     ждём стримы журнала → уже финализирован → коммит
     Dispatch вернул ошибку (откат) → ask отменяет генерацию

tx3  Dispatch(llm.error)                                     ← ask, если tx2 откатилась, ответ неполный или прерван
```

Что здесь видно:

- **Порядок внутри tx.** Инжектор выше `MinInt`, поэтому `llm.system` целиком обработан (`addSystem` уже дописал
  фрагмент) до того, как `addUser` снимет снимок. Инжектору, которому нужна долгая работа (поиск, файлы),
  этого мало: он задерживает `user.message` через `bus.Stop`, делает работу в async и в следующей tx
  отправляет `llm.system` и отпускает сообщение через `EmitIn` ниже своего priority (контракт — `contracts/llm`).
- **Атомарность.** Откатится tx1 — `OnAbort` уберёт сообщение и фрагмент из контекста, `anthropic.request`
  в async не попадёт, запроса к API не будет. Откатится tx2 — ответ не попадёт в `m.dialog`.
- **Снимок в событии.** `ask` работает параллельно со следующими tx, поэтому берёт параметры запроса из
  `anthropic.request`, а не читает `m.dialog`, который трогают только sync-обработчики.
- **Стрим и коммит.** tx2 не коммитится, пока модель не закончила ответ: это ждёт и `addAnswer`, и сам коммит (шаг 4 в [Как проходит tx](#как-проходит-tx)).
  Живой показ имеет priority выше `addAnswer`, иначе получил бы стрим только после его конца.
- **Отмена ответа.** Событие отмены через шину не пройдёт — tx2 держит очередь до конца стрима. Отмена ctx
  `Dispatch(user.message)` тоже не поможет: tx1 давно закоммичена, а async получают ctx без отмены.
  Поэтому фронтенд отправляет сообщение с `ctx, stop := llm.WithTurn(ctx)` и по Ctrl+C вызывает `stop()`:
  `ask` привязан к этому ctx хода, его отмена обрывает запрос к API, и стрим кончается раньше. tx2 при этом
  отправлена с ctx модуля, не хода, и коммитится: сказанное до отмены остаётся на экране и в `m.dialog`,
  модель видит, где её прервали. Следом уходит `llm.error` «interrupted». Когда ответ и ошибка ушли, `ask` вызывает `llm.End`:
  `llm.Turn(ctx).Done()` закрывается, и фронтенд знает, что ход окончен и Ctrl+C пора отдать на выход.

## Dispatch и ctx

- `Dispatch(ctx, ev)` ждёт предыдущую tx, открывает новую и возвращает `nil` при коммите или причину отката.
- ctx ограничивает и ожидание, и саму tx: дедлайн откатывает tx. Но `Dispatch` вернётся только после того,
  как текущий обработчик сам вернёт управление — обработчик, игнорирующий ctx, держит всю шину.
- `Dispatch` из sync-обработчика с его ctx (или с `WithoutCancel` от него, пока tx жива) возвращает
  `bus.ErrNestedTx`. С `context.Background()` вложенность не распознать — будет вечное ожидание.
- `Dispatch` из async-обработчика или из горутины, пережившей tx, — нормальный путь.

## Ошибки

| Значение | Что значит |
|---|---|
| `bus.Stop` | возвращает sync-обработчик: задержать событие; это не ошибка, tx продолжается |
| `bus.ErrNestedTx` | `Dispatch` вызван изнутри текущей tx |
| `tx.ErrClosed` | `Emit` на откатывающейся или завершённой tx; при откате оборачивает причину (`errors.Is` работает для обоих) |
| `bus: panic: ...` | паника в обработчике или фильтре; в тексте есть стек. Паники в `OnAbort` добавляются к ошибке через `errors.Join` |

## Чек-лист

- Долгое и внешнее (LLM, тулы, пользователь) — не ждать в sync-обработчике: задержать через `bus.Stop`
  или вынести в async + `Dispatch`.
- Побочные эффекты наружу — только в async.
- Изменил состояние в sync-обработчике — сразу `t.OnAbort(откат)`.
- В `Emit` передавать ctx обработчика; `Tx` не трогать из других горутин.
- Работа дольше tx — `context.WithoutCancel(ctx)`.
- Писатель стрима — отдельная горутина, канал закрывать всегда (и при ошибке).
- Приоритеты — именованные константы; у перехватчиков — уникальные.
- Обработчики уважают ctx, иначе дедлайн не спасёт шину.
